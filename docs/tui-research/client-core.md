# client-core: how much of the web client is React-free, and where the shared package boundary should sit

Repo: `/work/projects/platform`. All paths below are repo-relative unless absolute. Line numbers are from the working tree at HEAD `e9cfba70` plus the uncommitted plan-077 work (the `features/chat/environment/` folder is deleted in the working tree and `transport/chat-transport.ts`, `transport/create-chat-transport.ts`, `state/active-transports.ts`, `providers/transport-*.tsx` are the untracked replacements).

## 1. Summary

- `apps/web/src/lib/` is 7,995 non-test lines across 51 modules. By line count roughly **58% is pure** (runs in Bun with no shim), **17% needs a shim** (a Vite `import.meta.env` read, a `localStorage` call, a `toast`, or a `window.addEventListener` that is already guarded), and **25% is DOM/React-bound** and belongs to the web app only (focus service, file-open-intent, platform bridge, fonts, clipboard, React error reporting, file icons).
- The chat feature's non-component layers are larger and cleaner than `lib/`: `transport/` (997 lines) is portable except for four `WebSocket`/`MessageEvent` global references that already have an injection seam (`createSocket`, `orchestration-rpc-client.ts:53`); `state/` (4,541 lines) is portable except for six `localStorage` sites and three guarded `beforeunload` hooks; `utils/` (10,570 lines) is roughly 80% pure domain logic (projection writers, timeline derivation, command builders, pending approvals, model selection) with a well-separated DOM tail (image compression, Lexical editor actions, clipboard serialization, DOM fragment links).
- `packages/contracts` (36 modules, one `.` export, deps `valibot` + `minimatch`) and `packages/observability/env` are already runtime-neutral and are the correct foundation. Nothing in contracts touches `window`/`document`/`localStorage`; the only hit is the setting id string `'window.transparency'` (`packages/contracts/src/settings/keys.ts:367`).
- **TanStack Query:** neither reference TUI uses it. t1code's `packages/client-core` has no TanStack dependency; its TUI holds the snapshot in React `useState` fed by `transport.request(getSnapshot)` (`references/t1code/apps/tui/src/ui.tsx:4872-4910`), while its web app wraps the same transport in `queryOptions` (`references/t1code/apps/web/src/lib/serverReactQuery.ts`). opencode's TUI uses a Solid store (`references/opencode/packages/tui/src/context/sync.tsx:70`). For us, `@tanstack/query-core` 5.101.0 is already installed transitively and `QueryClient`/`queryOptions`/`QueryObserver` run without React, so the chat `queryOptions` modules can move as-is if the package depends on `@tanstack/query-core` instead of `@tanstack/react-query`. The chat read model itself does not use TanStack at all: it is a Zustand store fed by WebSocket subscriptions, which is exactly the shape a TUI wants.
- **Environments layer:** plan 077 is mostly landed in the working tree. The origin is a runtime value (`activeServerOrigin()`/`setActiveServerOrigin()`, `apps/web/src/lib/client.ts:20-26`) but is _seeded_ from `import.meta.env.VITE_SERVER_URL` at module scope (`client.ts:11`), and the environments store captures it at module scope too (`lib/environments/state/store.ts:31`). A TUI needs both seeds to become constructor arguments. The bigger blocker is server auth: `apps/server/src/auth.ts:75-76` rejects any request or WebSocket upgrade with **no `Origin` header** as `UNAUTHORIZED`, and Bun/Node `fetch`/`WebSocket` send none by default. A TUI must either send a synthetic allow-listed `Origin` (treaty `headers`, and `createSocket` for the RPC socket) or the server needs a non-browser principal. The comment at `auth.ts:97-104` says the token mode was deliberately deleted and real sessions are strategy milestone M4.
- Drift found: `apps/web/src/features/chat/state/server-connection-store.ts` (89 lines) and `apps/web/src/features/chat/state/server-restart-invalidation.ts` (41 lines) have **zero non-test consumers**. Plan 077 (`plans/077-environment-runtime-origin.md:173-181`) says they are deleted and folded into `lib/environments/state/store.ts`; the fold happened, the delete did not. Their tests still run against dead code.

## 8. The TanStack Query question

- **t1code**: `packages/client-core` has no TanStack dependency; `apps/tui` has none either (`apps/tui/package.json`); the TUI keeps the snapshot in React state refreshed via `transport.request(...)` (`ui.tsx:4896-4910`); `apps/web` layers `@tanstack/react-query` on top in app code (`apps/web/src/lib/serverReactQuery.ts`). Answer: **the shared core is query-library-agnostic; TanStack is a web-app choice.**
- **opencode**: no TanStack anywhere in the TUI (`packages/tui/package.json` deps are opentui/solid/effect/remeda); Solid `createStore` is the cache.
- **Ours**: the chat read model is not a TanStack cache. It is `chat-projection-store.ts` (Zustand) fed by `shellStream`/`threadDetailStream` subscriptions, so the TUI's main surface never needs TanStack. TanStack appears only in the request/response side: 11 modules (`grep queryOptions|@tanstack/react-query` under chat utils, chat-mode utils, lib): `composer-skills.ts`, `project-entry-query.ts`, `provider-auth-query.ts`, `provider-query.ts`, `session-search-query.ts`, `lib/query-state.ts`, `lib/recent-folders-query.ts`, `lib/file-snapshot-query-cache.ts`, `lib/file-open-intent/state/service.ts`, `lib/environments/state/server-restart-invalidation.ts`, `lib/environments/state/query-clients.ts`. Every one of them imports `QueryClient`/`queryOptions`/`Query` — all exported by `@tanstack/query-core` 5.101.0 (present in `node_modules/@tanstack/query-core`). `queryFn: ({ client }) => …clientForQueryClient(client)` (`provider-query.ts:19`) is the pattern that binds a query to its origin's Eden client without React.
- Recommendation: `client-core` depends on `@tanstack/query-core`; it exports `queryOptions` builders and `queryClientFor(origin)`. The web keeps `@tanstack/react-query` (`useQuery` over the same options; `QueryClientProvider` at `active-environment-application.tsx:23`). The TUI either (a) uses `QueryObserver` from query-core with `useSyncExternalStore` (OpenTUI+React) or a Solid signal (OpenTUI+Solid), or (b) ignores query-core for the few one-shot reads and calls the `fetch*` functions directly. Both work because the builders and the fetchers are separate exports.

The WS upgrade is checked the same way via `socket.data.headers.origin` (`auth.ts:67-69`, `originFromWebSocketData` L87-93) and closes with 1008 on failure (`orchestration/ws-rpc.ts:97-103`), which the RPC client maps to `ORCHESTRATION_WS_UNAUTHORIZED` (`orchestration-rpc-client.ts:756-764`) and the supervisor treats as `blocked` (`stream-reconnect.ts:20-25`). A Bun TUI has to send `Origin` on both `fetch` (treaty `headers` option, already a function at `client.ts:16`) and the RPC socket (`createSocket` option → `new WebSocket(url, { headers })`, which Bun supports). The alternative — a `local-process` principal or the token mode the comment at `auth.ts:97-104` says was deleted — is a server change; plan 078's SSH-forward model (`docs/environments-and-remote-plan.md:152-166`) assumes an origin allowlist, so the synthetic-Origin approach is the one that needs no server work. Either way this is a decision the TUI plan must record.
3. **Identity/handshake** already works for a TUI: the `connected` frame carries `environmentId`, `serverInstanceId`, `protocolVersion` (`orchestration-rpc-client.ts:400-417`), and `/health` returns `healthDescriptorSchema` (`packages/contracts/src/index.ts:313`).
4. **Persistence scoping** is not done (plan 078 §"Scoped persistence"); the TUI's file-backed `KeyValueStorage` should be keyed by `environmentId` from the start rather than inheriting the web's unscoped keys (`workspace-cache-storage.ts:5-7` is at version 19 and drops on mismatch, no migration).
5. **Dead duplicates** to delete: `features/chat/state/server-connection-store.ts`, `features/chat/state/server-restart-invalidation.ts` and their tests.

## 10. Risks

- `zustand`'s root import re-exports `zustand/react` (`node_modules/zustand/esm/index.mjs`), so every store that does `import { create } from 'zustand'` (13 in chat/state, 12 in chat-mode/state, 1 in lib/environments) drags React into the package unless rewritten to `createStore` from `zustand/vanilla`. Mechanical but touches every store file and every `useXStore(selector)` call site in components (they become `useStore(xStore, selector)`).
- `@tanstack/react-pacer/debouncer` (`index.js`) imports React hooks; the four stores using `Debouncer` must import from `@tanstack/pacer/debouncer` (already installed at 0.21.1 as a transitive dep; needs to be a direct dep of the new package).
- `getClient()` ambient default is used in 67 non-test places across 15 modules (`grep -rn "getClient()"`). Moving `file-server.ts` and the query builders with `client: Client = getClient()` defaults keeps a hidden global in the shared package; dropping the default forces the web to thread `clientForQueryClient(queryClient)` everywhere. The test seam (`apps/web/test/fixtures.ts:31-39`, `test/env/dom.ts:21-26`) depends on `setClient` and must move with the registry.
- `import.meta.env` inside a workspace package would be inlined by Vite for the web but undefined under `bun` for the TUI; the package must not contain any (`client.ts:11`, `client-logging.ts:78-181`).
- `ProjectId` derivation (`stable-path-hash.ts:1-8` + `command-builders.ts` `workspaceProjectId`) is a join key to server rows. If the TUI resolves paths differently (symlinks, trailing slash, `~`), it silently creates a second project. `features/workspace/utils/path.ts:20-22` normalises only trailing slashes on purpose.
- Eden `Date` revival (`eden-events.ts:13-18`) applies to a Bun treaty client as well; every contract-typed read must keep `normalizeDates: true`.
- The chat projection cache writes on every store change with a throttle (`chat-projection-store.ts:296-323`) and flushes on `beforeunload`; a TUI backing store must be cheap to write or the throttle constant needs to become host-tunable.
- `server-sockets.ts` uses DOM event types; under a Bun-only tsconfig (`@types/bun`) the names resolve, but a package tsconfig that includes neither `lib.dom` nor `@types/bun` fails to compile. Pin the package tsconfig `lib` to `["ESNext"]` + `types: ["bun"]` or define structural `WebSocketLike` types the way t1code does (`wsTransport.ts:30-44`).
- Line counts in §3/§4 are approximate classifications from import scans, not a build; the definitive check is a `tsgo --noEmit` of the extracted package with `lib: ["ESNext"]` and no `dom`.

## 11. Open questions

1. Synthetic `Origin` header from the TUI (no server change) or a non-browser principal on the server (`auth.ts:97-104` says token mode was deleted deliberately)? Which one does plan 078's SSH-forward story prefer?
2. Does the TUI own `@tanstack/query-core` or call the `fetch*` functions directly? The answer decides whether `queryClientFor`/`clientForQueryClient` go into the package or stay web-side.
3. OpenTUI + React (t1code) or OpenTUI + Solid (opencode)? With React the Zustand stores can stay as `create()`-built hooks and the vanilla rewrite is optional; with Solid the vanilla rewrite is mandatory.
4. Where does the TUI persist per-viewer state (drafts, prompt stash, read stamps, rail collapse) — a JSON file under XDG state, or nothing? This decides whether `KeyValueStorage` is a required or optional port.
5. Should the TUI log through `/_log/ingest` like the web (`client-logging.ts:150-156`) or through `@workspace/observability` `initializeObservabilityRuntime` with `source: 'tui'` into `logs/`? The latter matches the JSONL conventions in CLAUDE.md and needs no server round-trip.
6. Menu models (`features/menus/utils/model.ts`) type items with phosphor `Icon`. Do we split the model into an icon-free core (id, label, command, disabled) so `session-menu.ts`/`project-menu.ts`/`message-menu.ts` can move, or does the TUI re-derive menus?
7. Delete `chat/state/server-connection-store.ts` + `server-restart-invalidation.ts` now (dead), or leave for the 077 close-out pass?
