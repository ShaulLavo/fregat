### Notes

- SCOPE VERDICTS ASKED FOR, stated plainly. chat.defaultRuntimeMode = application: it selects the provider session's permission posture and is read into the adapter session config (codex.ts:333, claude.ts:396), so a cloned repo must never be able to set 'full-access'. providers.instances = machine: binaryPath and environment reach Bun.spawn via provider-adapter-registry.ts:310-320 and drivers/codex.ts:49-53, and both are per-machine facts (paths, binaries) that must never sync. Neither can be window under the plan's standing rule. I also pulled chat.defaultInteractionMode up to application on the same permission axis even though the plan does not name it — plan vs default decides whether the agent acts before approval, and it rides the same adapter session config.
- DEFAULT-VERIFICATION METHOD: every `verified: true` row above was read at fda1523 (git rev-parse confirmed) by opening the defining file, not by trusting any prior inventory. Nothing in this group came back missing, so there is no `verified: false` row.
- THE ONE TRAP AN IMPLEMENTER WILL HIT: chat.attachments.maxPerMessage and chat.attachments.maxBytes are consumed inside valibot schemas built at module import (packages/contracts/src/chat-model.ts:51, :69, :81, :86) and are re-derived a second time at module scope on the client (MAX_CHAT_ATTACHMENT_ENCODED_BYTES, apps/web/src/features/chat/lib/chat-input-attachment-limits.ts:42). A settings value that only moves the browser check while the wire schema stays frozen at 8/10MB is worse than no setting — it turns a clean client-side refusal into a mid-turn server rejection. Either mark both requiresRestart (what I did) or rebuild the schema per request; do not ship the half.
- chat.assistantDeliveryMode is the odd row: the behaviour is complete and tested but has no production configuration path at all. engine.ts:383 is the only non-test construction of ProviderRuntimeIngestion and it never passes the option, so 'buffered' is currently reachable only from tests. I registered it because the task asked whether it exists — it does — but treat it as plumbing an existing dead branch, not as a new feature, and note the mode is captured into a readonly constructor field so live updates need the instance rebuilt.
- models.hidden and models.order are dead in BOTH directions at fda1523, confirmed by reading both ends: model-rows.ts:14-25 derives rows only from the prefs (so the section can never populate on a fresh install) and provider-model-options.ts:75-90 takes only provider snapshots (so the picker ignores them). Phase 7 is real feature work on both ends, not wiring. Same for the provider env editor: provider-row.tsx renders an enable Switch and nothing else, so the env UI the redaction work protects does not exist yet.
- launchArgs (packages/contracts/src/settings.ts:58) is stored, validated, uniquely-defaulted and round-tripped — and read by nothing. `rg launchArgs apps packages -g '!tests'` returns the schema line and the empty default in provider-rows.ts:46, full stop. I did not give it its own registry id because it is a field of providers.instances, but the Phase 7 decision (wire it into driver.create or delete it) has to be made before the provider editor ships, or the UI will offer a field that does nothing.
- The original `providerInstances` and `keybindings` document sections have been replaced by the flat registry keys `providers.instances` and `keybindings.overrides`. The current schema is generated from `packages/contracts/src/settings/keys.ts`.
- DELIBERATELY EXCLUDED, with pointers so nothing is lost. (a) CHAT_IMAGE_MIME_ALLOWLIST (chat-input-attachment-limits.ts:16) — not a preference: the list is dictated by what the Claude SDK accepts and the file says 'Do not widen'. Making it settable creates a knob whose only effect is a hard-failed turn. (b) QUALITY_LADDER and FALLBACK_SCALE_STEPS (image-compression.ts:27, :30) — module-private encoder tuning with no seam; register only if someone wants to tune compression from JSON. (c) The chat cache/engineering constant block: apps/web/src/features/chat/state/chat-cache-constants.ts:1-21 (12 caps, e.g. CHAT_MESSAGE_CACHE_LIMIT 2000, CHAT_PROJECTION_CACHE_THREAD_LIMIT 200, CHAT_PROJECTION_CACHE_PERSIST_MS 500), plus timeline-scroll-anchoring.ts:12-32, stream-reconnect.ts:6, chat-proposed-plan.ts:5-7, user-message-collapse.ts:5-6, markdown-highlight-cache.ts:11-12, orchestration-rpc-client.ts:29-34. These are all chat.\* and all belong in the plan's ~65 `internal` constants bucket, but they are a coherent separate sub-batch and were not in this section's brief — flagging them here rather than silently dropping them.
- chat.diff.defaultScope has exactly one expressible value today. The scope schema is a variant (thread-diff-scope-storage.ts:19-26) whose 'turn' arm requires a concrete turnId, and the comment at :14-18 explains that the branch-diff arm was deliberately left out because nothing on the client renders it. So the enum has one member. Register it as an enum anyway so adding the branch arm later is a value change, not a type change.

- BUT THE LOSS IS NARROWER THAN 'DESTROYS SCROLLBACK', AND THE PLAN SHOULD SAY WHICH. The pty is NOT killed: TerminalService keeps persistentSessions keyed by (rootPath, sessionId) and a reconnect hits the `existing` branch and re-attaches (apps/server/src/terminal/service.ts:135-140). On attach the server replays its buffered output (:265-266), but that buffer is capped at TERMINAL_REPLAY_BUFFER_BYTES = 256 KiB and older chunks are shifted off (:64, :339-351). Precise statement: a theme switch keeps the shell and its state, and truncates visible history from the client's 10,000-line scrollback down to the last ~256 KiB of output. Write that in Phase 5 instead of 'destroys scrollback', or the fix will be measured against the wrong claim.
- THE FIX THE PLAN PROPOSES DOES NOT WORK AT THE PINNED VERSION. Phase 5 says 'apply the palette through `terminal.options.theme` + `refresh()`'. Neither half exists in ghostty-web@0.4.0 as installed (patch applied). The only live theme path is the renderer-level `setTheme(theme: ITheme)` (dist/index.d.ts:70) reached through the public `terminal.renderer`, followed by a forced render — and even that is likely partial, because the WASM terminal is separately configured with palette colors parsed at construction (parseColorToHex feeds the wasm config), so a renderer-only setTheme can leave the wasm-side palette stale. Our own patch (patches/ghostty-web@0.4.0.patch) already edits the renderer for the outline cursor and transparent background but does not touch theme. - SCOPE, STATED EXPLICITLY AS ASKED: terminal.integrated.defaultProfile, .shellArgs, .env, .cwd and .inheritEnv are MACHINE, never window. ### Notes

- SCOPE JUDGEMENT CALL — the one thing that needs an explicit ruling. The plan's hard rule ('any value that reaches process spawn/exec/env/keymap is application or machine, never window') collides with the fact that essentially every search preference ends up as argv on a spawned `rg` or `fd`. I drew the line at _what kind_ of argv: (a) fixed flags toggled by a boolean (`--ignore-case`, `--word-regexp`) and (b) per-query glob payloads the user can already type into the visible filter box today are window; (c) values that are server configuration baked into every invocation regardless of the request (`files.exclude` → `--exclude`/`--glob !…`, `search.maxFileSizeBytes` → `--max-filesize`) and (d) anything that _un-hides_ files (`search.useIgnoreFiles`) are application/machine. Rationale for (b): a glob is a separate argv element after `--glob`, spawned through `Bun.spawn` with no shell (apps/server/src/fs/search-tool-runner.ts), so it cannot select a binary, set an env var, or become a flag; and the identical capability is already exposed to anyone at the keyboard through the search filter row. If the reviewer reads the rule literally instead, move search.include/search.exclude/search.defaultMatchMode/search.caseSensitive/search.wholeWord to `application` — but then per-project search excludes, the single most-wanted workspace setting, become impossible.
- RESIDUAL RISK of window-scoped globs, stated plainly so it is a decision and not an oversight: a cloned repo shipping `.platform/settings.json` with `search.exclude: ['**/*.ts']` silently hides files from the search UI _and_ from the agent's search results. That is a suppression attack, not code execution, and the plan's Phase 4 'also modified in <scope>' indicator is the mitigation — the search panel must show that its filters came from workspace settings, not just the settings page. Do not ship window-scoped globs without that indicator.
- PER-WORKSPACE vs MACHINE, the split this group was asked for. Naturally per-workspace (window): search.defaultMatchMode, search.caseSensitive, search.wholeWord, search.include, search.exclude, search.maxResults, search.quickOpen.maxResults — all six of the first ones are ALREADY persisted per root path today, in localStorage under `platform.workspace-state.v16.search:<rootPath>` (apps/web/src/lib/workspace-cache.ts:44,73-75; schema `cachedSearchBufferStateSchema` at workspace-cache.ts:163-183). The product already believes these are per-project; the registry just moves where that belief is stored. Machine limits (never per-workspace): files.watcherEnabled, files.maxTextFileBytes, files.treeConcurrency, search.maxFileSizeBytes — all four are constructor-time `private readonly` fields on FileSystemService, three of them env-driven from apps/server/src/index.ts:18,21,22.
- BOOT-CRITICAL SET. files.watcherEnabled, files.maxTextFileBytes, files.treeConcurrency, search.maxFileSizeBytes and files.exclude are all read before or during `createApp`/module import and stored immutably. None can be delivered over the settings SSE. They belong on the plan's boot-critical list and all carry requiresRestart: true. `files.exclude` is the worst of them: `watcherIgnoredChildGlobs` is computed at _module import_ time (apps/server/src/fs/watch.ts:23-26), so it is frozen before any settings file is read.
- MIGRATION TRAP for Phase 6. The six search prefs live in a strictObject localStorage schema (`cachedSearchBufferStateSchema`, workspace-cache.ts:163) at CACHE_VERSION 16 (workspace-cache.ts:41). Removing the fields without bumping CACHE_VERSION makes every stored search buffer fail `v.safeParse` and get dropped by `readCacheEntry` (workspace-cache.ts:454) — which also throws away the cached match list. Per the repo's greenfield rule that is acceptable (delete the bad state), but bump CACHE_VERSION in the same commit so the failure is a clean drop rather than a per-user error toast via `reportError`.
- THE 200 CEILING is a real gate, not a detail. `limitQueryValueSchema = integerQueryValueSchema('50', 200)` (apps/server/src/fs/contracts.ts:6) rejects rather than clamps. Both search.maxResults and search.quickOpen.maxResults sit exactly at that ceiling today, so any registry schema that permits a larger value ships a setting that 4xx's the moment a user raises it. Either pin the schema max at 200 or raise the route bound in the same commit.
- TWO ENV NAMES FOR ONE VALUE. `FS_DEV_MAX_TEXT_FILE_BYTES` (apps/server/src/index.ts:21) and `MAX_TEXT_FILE_BYTES` (apps/server/src/fs/service.ts:71) both configure files.maxTextFileBytes, on different code paths, with only the second one validated and warned about. Independently, GitService keeps its own duplicate `DEFAULT_MAX_TEXT_FILE_BYTES = 209_715_200` (apps/server/src/git/service.ts:110) that happens to match. Collapse all three onto the descriptor when registering the key. Related to the plan's Phase 2 note that turbo.json has no PLATFORM*\*/FS*\* passThroughEnv entries — FS_WATCH, FS_TREE_CONCURRENCY and both max-bytes names have the same latent cache bug.
- DELIBERATELY EXCLUDED, with reasons. (1) `useWorkspaceIndex` (apps/server/src/fs/contracts.ts:62) is not a preference — it is chosen per call from the picker's scope (apps/web/src/components/file-picker/picker-search.ts:85) and the index itself is enabled only when a workspaceRoot is configured (apps/server/src/fs/service.ts:442-444). (2) Recents limits are three different call-site constants for two different UIs — 30 in apps/web/src/components/file-picker/data-helpers.ts:20, 40 in apps/web/src/lib/recent-folders-query.ts:7, route default 20 capped at 50 in apps/server/src/fs/contracts.ts:7,169 — so there is no single coherent key until those are unified; register it only if someone unifies them first. (3) Streaming batch cadence (SEARCH_FIRST_BATCH_DELAY_MS 0 / SEARCH_STEADY_BATCH_DELAY_MS 48 / SEARCH_FRAME_FALLBACK_MS 16, apps/web/src/features/search/search-buffer-runner.ts:21-23) and DIRTY_BUFFER_DEBOUNCE_MS 220 (use-run-dirty-search-buffer-overlay.ts:21) are frame-scheduling constants, not settings. (4) CONTENT_INDEX_RG_EXCLUDE_GLOB_LIMIT 512 (apps/server/src/fs/search.ts:95) bounds index-derived globs only, never user input. (5) There is no search-as-you-type debounce key to register: `useRunSearchBuffer` fires off the committed `query` in an effect (apps/web/src/features/search/use-run-search-buffer.ts:27) with no wait, so `search.searchOnType`-style keys would be new features.
- NO SMART CASE, NO FORMAT-ON-SAVE. `--ignore-case` is applied unconditionally whenever caseSensitive is false (apps/server/src/fs/search.ts:736); there is no smart-case path to expose. `editor.formatOnSave` — listed in the plan's Phase 6 paragraph next to the files.autoSave keys — likewise has zero occurrences at fda1523 (`rg formatOnSave` over apps/ + packages/ returns nothing); it belongs to the editor group but the plan's 'these three are new features, estimate separately' claim is confirmed on all three.
- The existing settings document (packages/contracts/src/settings.ts:117-121) contains only providerInstances, models and keybindings. Every key in this group is new to the registry — none is a rename of an existing stored key, so there is no read-compat concern, only the localStorage deletions noted above.

### Notes

- CORRECTION to the brief's premise about apps/server/src/lsp/registry.ts: it does NOT read PLATFORM_LSP_CONFIG/FS_LSP_CONFIG once at construction. `lspServersForEnvironment(env = process.env)` (registry.ts:489) calls `lspConfigFromEnvironment` (:614) on every invocation, and it is invoked from inside `matchLspServer` (:475), i.e. once per /lsp/match request. The env read is already per-request. The ONE thing genuinely read once at module load is `const useTyForPython = truthy(process.env.FS_EXPERIMENTAL_LSP_TY)` (registry.ts:55), and because `experimentalFilteredServers` ORs it with the per-call env (:511) it is a one-way latch that cannot be un-set in-process. That latch, not the config read, is what forces requiresRestart on lsp.experimental.tyForPython.
- Server-definition count: the `lspServers` array holds 37 definitions (registry.ts:69-467), not 36. Only 36 are ever active at once because `experimentalFilteredServers` (:510-515) removes exactly one of the mutually-exclusive Python pair — `ty` normally, `pyright` when the TY experiment is on. Any registry test that asserts a count must account for that filter.
- WHAT A CHANGE TO lsp.servers MEANS FOR RUNNING SESSIONS (the brief's specific question): nothing, until the process dies. Sessions live in a module-level `pooledSessions` Map keyed `${match.server.id}${match.root}` (proxy-session.ts:77, :694-711, :719-721). Editing `command`, `args`, or `env` for a server id does not change that key, so `pooledLspProxySession` returns the EXISTING child process — spawned with the old command and old environment — to every new connection for that root. Setting `disabled: true` only removes the definition from `matchLspServer`'s candidate list (:496-500), which stops NEW roots from starting a server but does not touch a live one. The session only goes away on idle timeout (120s after the last connection drops, :553) or on process exit. There is no exported disposer: `PooledLspProxySession.dispose` is private (:574) and `removePooledSession` (:713) is module-internal. So wiring lsp.servers requires (a) a new exported `disposeLspSessionsForServer(id)` / `disposeAllLspSessions()`, (b) a settings-change hook that calls it, and (c) a client decision — reconnect the editor LSP socket automatically, or surface an explicit 'Restart Language Server' action. Without (a)-(c) the settings page will look like it works and silently do nothing for anyone with a file already open.
- THREE INDEPENDENT 500ms CONSTANTS, all meaning different things, none currently shared: (1) `DEFAULT_SLOW_MS = 500` (packages/observability/src/config.ts:49) — the sampling KEEP threshold, 'never drop an event slower than this'; (2) `defaultLogsFilterState.slowMs = 500` (apps/web/src/features/logs/log-filter-params.ts:19) — the dashboard's slow-count threshold sent on the query; (3) `defaultSlowMs = 500` (apps/server/src/observability/log-reader.ts:42) — the reader's fallback when the query omits slowMs. I registered (1) and (2) as separate keys and left (3) as the reader's fallback. Do not collapse them: (1) is a retention decision made at write time and (2) is a display decision made at read time. If they are unified, (3) has to be deleted, not aliased.
- logs.server.level is registered with verified:false on purpose. The brief asked for 'client and server log levels', but there is no server minimum level in the code: `initLogger` in packages/observability/src/runtime.ts:50-68 passes no `minLevel`, and `ObservabilityConfig` (config.ts:14-37) has no level field. The server's equivalent is per-level sampling (`sampling.rates`, runtime.ts:59-65) with error/warn hardcoded at 100. Either drop the key or treat it as new work in Phase 6 — do not register it as a passthrough.
- logs.server.debugSampleRate is the one observability config field with no env override at all: config.ts:70 is a bare `production ? 0 : 100` with no `observabilityEnv(env, ...)` call, unlike every sibling. Wiring it needs the config read added, not just the settings read. It is also why debug logging cannot currently be turned on in a production build by any means.
- PARSER LENIENCY THAT THE REGISTRY SCHEMAS SHOULD REPLACE, NOT PRESERVE: `positiveInteger` (config.ts:125-132) and `nonNegativeInteger` (:134-141) silently fall back to the default on a bad value, and `postHogMode` (:152-155) silently means 'logs' for anything that is not exactly 'events'. Under the plan's per-key-fallback read rule that is roughly the right behaviour for the FILE layer, but the registry schema should still reject the value so the settings page can say 'invalid' instead of showing the default as though the user's input were accepted. Also note the positive/non-negative split is real: postHogRetries legitimately accepts 0, the others do not.
- SCOPE JUDGEMENT CALLS. (a) Every lsp._ key is application or machine, none window — mandatory for lsp.servers (command + env spread over process.env at registry.ts:593-600 = arbitrary execution) and lsp.experimental.tyForPython (picks which Python binary spawns), and I extended it to lsp.serverPriority because reordering picks which binary spawns even without a command string, and to lsp.enable because it decides whether any server spawns. (b) lsp.idleTimeoutMs and lsp.servers are `machine` not `application`: they govern child-process lifetime, binaries, and paths, which the plan's definition of machine names directly. (c) telemetry.postHog.host is `application` even though it is not literally spawn/exec/env — it is where every log event is POSTed, so a workspace-settable value is a log-exfiltration channel. Add it to SERVER_CONSUMED_SETTINGS with an explicit comment so the registry test covers it; the literal wording of the standing rule does not catch it. (d) logs.server.dir is `machine` (filesystem path chosen by a cloned repo would be a write primitive). (e) Only logs.dashboard._ are `window` — pure client UI state that never reaches spawn, exec, env, or the keymap.
- EXCLUDED DELIBERATELY. `logs.dashboard.defaultSearch` (log-filter-params.ts:17, default `''`): a persisted default search silently hides rows on every panel open and is the kind of setting that generates 'the logs are broken' reports; leave it session-local. `defaultEventLimit = 200` / `maxEventLimit = 1_000` / `timelineBucketCount = 48` / `maxBreakdownItems = 12` (apps/server/src/observability/log-reader.ts:40-44): server-side reader constants with no user-visible meaning; maxEventLimit matters only as the clamp on logs.dashboard.eventLimit and is documented there. The client's `serviceName = 'platform-web'` (apps/web/src/lib/client-logging.ts:24) is hardcoded with no env read, so there is no client counterpart to logs.server.service. The `sensitiveFields` redaction set (client-logging.ts:28-47) and `maxStringLength = 2_000` (:26) are security policy, not preferences — deliberately not settings, and a workspace-settable redaction list would be an obvious hole.
- PHASE PLACEMENT. Everything here is Phase 6 (the plan's 'files / search / chat / lsp / telemetry / window batch') except two keys pushed to Phase 7: `lsp.servers`, which is a record of objects carrying command/args/env and needs the Phase 7 record editor plus the new session-disposal machinery, and `lsp.serverPriority`, which is a list-valued key needing the Phase 7 list editor. lsp.enable is the only key in this group that is genuinely new behaviour rather than plumbing, so it should be estimated with the plan's other feature-shaped keys (files.autoSave, editor.formatOnSave) rather than with the ~80 plumbing keys.
- requiresRestart is true for every telemetry._ and logs.server._ key because `initializeObservabilityRuntime` (runtime.ts:44-72) builds the drain and calls `initLogger` exactly once at boot, and true for logs.client.level because `initializeClientLogging` is latched by the module-level `initialized` flag (client-logging.ts:49, :59-61). The one asymmetry worth surfacing in the UI: telemetry.enabled is re-read live on the client (`clientLoggingEnabled()` is called on every `emitClientLog`, client-logging.ts:131) but not on the server — so turning telemetry off stops browser events immediately and server events only after a restart. Say that in the restart notice rather than implying both halves are stale.

### Notes

- ALL 68 keys above were verified by opening the defining file at fda1523 today. No key in this group is marked verified:false — every default listed exists in code at the cited line. Nothing here is a NEW FEATURE; the entire group is PLUMBING (hard-coded constants becoming registry-backed), which is why it is cheap despite its size.
- SCOPE JUDGEMENT — the hard rule bit harder than expected. Nine keys that read like harmless UI tuning actually pace process spawn and are therefore application, never window: git.status.staleTime / git.status.serverCacheTtl / git.branchRemoteState.staleTime (git status), git.pullRequest.pollInterval / .timeout / .supportCacheTtl (gh), git.upstreamFetch._ (git fetch), search.debounce / search.maxResults / search.quickOpen._ (rg), lsp.idleTimeout / lsp.diagnosticDelay (language-server children), terminal.integrated.detachedSessionTtl (PTY children), providers.auth.defaultMethod (claude auth login). A cloned repo setting search.debounce to 0 is one ripgrep per keystroke; setting git.status.staleTime to 0 is a git-status storm. I also put the plain TanStack Query defaults (workbench.query._, files.snapshotCache._) at application on the same reasoning one step removed — they all resolve to local-server requests, and a workspace-settable 0 is a self-inflicted DoS from hostile input. The only window-scoped keys I kept are the three that touch nothing but pixels: workbench.tooltip.delay and workbench.commandPalette.recentCommandsShown.

### Notes

- PHASE PLACEMENT CAVEAT: the plan's phase list never names `git.*`. Phase 6 is literally 'files / search / chat / lsp / telemetry / window', yet the Registry payload section (plan:919) lists `git.*` among the v1 namespaces. I placed every git key in Phase 6 — the only batch whose consumers (server git service, git panel, file tree) are all live — except the list-typed `git.baseBranchCandidates`, which needs Phase 7's list editor. Flag this back to the plan author: either Phase 6's name gains 'git', or git gets its own batch.
- SCOPE, THE BIG JUDGEMENT CALL: git is an exec surface end to end, so 28 of the 29 git keys are `application`. The one exception is `git.decorations.enabled` (window) — it only decides whether status badges paint in the tree and reaches no argv, env, or keymap. `git.path` is `machine` (a binary path, per the plan's own machine definition). Anyone porting VS Code's window-scoped `git.*` defaults into this registry would be importing the vector the plan's hard rule exists to close.
- THE CONFIRM KEYS ARE APPLICATION ON PURPOSE. git.confirmDiscard / confirmSync / confirmForcePush render dialogs, which reads like window scope. They are application because the _value_ decides whether a destructive or network git command spawns unprompted. A cloned repo shipping `{"git.confirmDiscard": false}` in .platform/settings.json plus one mis-clicked toolbar button is uncommitted-work loss with no prompt.
- INERT-KEY RISK: `git.confirmForcePush` has nothing to confirm. Force push does not exist anywhere — GitService.push builds only `push` / `push --set-upstream origin <branch>` (service.ts:553-560), and no route, contract, or UI carries a force flag. The plan's rule is 'a key is never registered inert', so this key must ship with a force-push command or be cut. It is listed because the parity matrix names it; it is the single key here I would drop first.
- THE PARITY MATRIX IS WRONG ABOUT AUTOFETCH. docs/editor-parity-gap-matrix.md:223 lists 'Auto-fetch ❌ missing'. It exists and is always on: UpstreamFetchScheduler throttles a real `git fetch <remote>` per (git common dir, remote) off every status read (service.ts:705, upstream-fetch.ts:25-97). What is missing is only the on/off setting, the period, and VS Code's all-repos-vs-current choice. That makes git.autofetch/autofetchPeriod plumbing, not new features — a meaningful estimate difference.
- CONFLICTING DEFAULT FOUND — git.diff.ignoreWhitespace. Server and routes default `false` (service.ts:262, orchestration/routes.ts:140,156) but the chat checkpoint client hardcodes `true` at three call sites (features/chat/lib/checkpoint-diff-query.ts:46,59,148), and the git panel's own diff path (service.ts:207-217) does not accept the flag at all. I registered `false` (git's own behaviour, and what the panel does today). The registry cannot paper over this: decide whether checkpoint diffs honour the key or are explicitly exempted, before Phase 6.
- DELIBERATELY EXCLUDED — blame. `git.blame.*` appears in the parity matrix's 'diff/blame options', but a repo-wide grep for 'blame' in apps/web/src and apps/server/src returns nothing outside tests. There is no gutter, no route, no service method. Any blame key would be inert by definition.
- DELIBERATELY EXCLUDED — SCM count badge, checkout-safety/auto-stash, remote management, and tags. All are whole missing features in the matrix with zero code to gate; their settings belong to whichever phase builds the feature, not to this registry batch.
- DELIBERATELY EXCLUDED — identity and layout constants that would orphan on-disk state if changed: CHECKPOINT_IDENTITY (checkpoint-store.ts:44-49, deliberately not the user's git identity so hidden refs never look authored by them), SESSION_WORKTREES_DIRECTORY = 'platform-worktrees' (worktrees.ts:25), and BASE_CONFIG_KEY = 'platform-base' (worktrees.ts:28). Changing any of these strands existing refs/worktrees/config, and this repo has no migration code by policy.
- DELIBERATELY EXCLUDED — `staleTime: Infinity` on the content-addressed queries (use-diff-document-diffs.ts:43,53; use-open-file-at-ref.ts:27). Those are keyed by git object id, so infinite freshness is correctness, not a tunable. Registering them would invite a user to break diff rendering.
- DELIBERATELY EXCLUDED — MAIN_WINDOW_TITLE = 'Platform' (apps/desktop/src/bun/index.ts:29). It looks like a cosmetic `window.title` key but it is load-bearing: attachWindowVibrancy finds the AppKit window by matching this exact NUL-terminated string over FFI (index.ts:157, vibrancy.ts:32-34). A user-editable title would silently break vibrancy attach with only a desktop.vibrancy.window-not-found log to show for it.
- DELIBERATELY EXCLUDED — the vibrancy tuning constants: UNDER_WINDOW_BACKGROUND = 21, ATTACH_ATTEMPTS = 40, ATTACH_RETRY_MS = 50 (vibrancy.ts:9,13,14). With transparent:false forced, the attached NSVisualEffectView never shows through, so these are inert today. Revisit them together with window.nativeVibrancy if CEF ever gains transparency without OSR.
- NO BOUNDS KEY, AS INSTRUCTED. index.ts:137-138 hardcodes `x: 0, y: 0` alongside the size; I registered defaultWidth/defaultHeight but not x/y, because position is where-you-left-it state and belongs with session state, not settings.json (plan:635-638). Note this also means the current shell always opens at 0,0 — a UX bug, not a settings gap.
- VERIFICATION LINE I DREW: verified:true means I opened the file at fda1523 and saw a literal equal to the default I report. verified:false means the default is inferred from unconditional behaviour (git.enabled, git.autofetch, git.decorations.enabled) or the behaviour does not exist yet (the three confirm keys, git.enableSmartCommit). Every window.* default is a verified literal in apps/desktop/src/bun/index.ts; only the titleBarStyle *value union\* is unverified, because node_modules is absent in this worktree and electrobun's typings could not be opened.
- NO SENSITIVE KEYS IN THIS GROUP. Nothing under git._ or window._ is a credential, so none carry `sensitive: true` and none touch the secrets.json split. Closest call is git.path, which is a machine-scoped binary path — dangerous, but not secret.
- WINDOW KEYS HAVE A SECOND READER. Every window.* key is read by the desktop shell *before\* the server or the web app exists (`new BrowserWindow` at index.ts:132 happens after waitForHttp, but the read must be synchronous and file-based). So the registry must be importable from apps/desktop/src/bun with no server dependency, and the plan's test that shell and server resolve the same defaults from the same registry (plan:649) is the guard. requiresRestart:true on all five until an applyWindowSettings request exists on DesktopRPC — today the RPC exposes only pickEntry (index.ts:123-130).
