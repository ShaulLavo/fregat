# Theme standardization research

Research date: 2026-09-12. Platform baseline: `a01bf78f63cb94b4985a925d2c8d9de66294230f` plus the existing working tree. The proposed work is in [Plan 115](../plans/115-palettes-as-data.md), [Plan 116](../plans/116-wallpaper-library.md), and [Plan 117](theme-bundles.md), which replaced Plan 104 on 2026-09-14.

The product direction is a named theme that supplies a complete appearance. Its colors, code highlighting, terminal colors, and wallpaper collection belong together. Light and dark are variants of that appearance. Customization starts from the selected theme and remains available without making every user assemble those parts.

The user's follow-up clarifies the limit of the inspiration: Platform keeps its own visual language. Omarchy informs theme packaging, palette sources, and wallpaper collections. Platform owns component design, layout, typography hierarchy, iconography, surface treatment, and motion. The importer adapts color roles to those rules; reproducing an Omarchy desktop screenshot is not its target.

## Omarchy supplies the strongest model for a complete theme

The official repository redirects from `basecamp/omarchy` to `omacom/omarchy`. This research uses commit `31bd80daa4613ffdee995ac27467fce5a2990806` on its current default branch, `quattro`. Local installed source under `/usr/share/omarchy` was also inspected without running theme commands.

An Omarchy theme coordinates the desktop, terminal, editors, and background collection. Its authored `colors.toml` supplies the palette. A resolver fills missing values, and templates distribute the colors to applications. Theme-specific configuration overrides generated templates. User templates provide another customization point. These are useful precedents for one definition with several renderer outputs. [Theme overview](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/manual/06-themes.md), [color resolver](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/bin/omarchy-theme-color), [template generation](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/bin/omarchy-theme-set-templates).

Each Omarchy theme has one mode. Tokyo Night declares dark; the built-in Rose Pine declares light and uses Dawn colors. Grouping authored light and dark variants under one Platform theme is our adaptation. Omarchy does not establish that every theme has a matching opposite mode. [Tokyo Night palette](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/themes/tokyo-night/colors.toml), [Rose Pine palette](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/themes/rose-pine/colors.toml).

The `backgrounds/` collection belongs to the theme. Users can add backgrounds, and a command advances through the combined collection. Applying a theme also updates its background. The palette is authored independently of the images; automatic palette extraction from a wallpaper is not the mechanism to copy. [Theme application](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/bin/omarchy-theme-set), [background cycling](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/bin/omarchy-theme-bg-next).

Editor integration sometimes names a third-party extension, such as `enkia.tokyo-night`, and otherwise generates a VS Code theme. An extension identifier does not contain syntax colors. Platform needs actual validated theme registration data or a reviewed mapping to an already bundled registration. [Tokyo Night editor descriptor](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/themes/tokyo-night/vscode.json), [VS Code integration](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/bin/omarchy-theme-set-vscode), [generated editor theme](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/default/themed/vscode-theme.json.tpl).

The reuse recommendation is a pinned importer, followed by local rendering. It accepts a repository and theme subdirectory, reads color and supported asset data, and emits Platform's own format. It does not run Omarchy installers, hooks, Lua, shell commands, or extension installation. Current Omarchy also distinguishes executable local customization from restricted installed themes. [Theme authoring rules](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/manual/43-making-your-own-theme.md).

The root has an MIT license with a copyright and notice-retention requirement. The inspected theme tree has no per-image provenance manifest. That leaves individual wallpaper redistribution unverified; it does not prove that redistribution is prohibited. Imported editor themes require their own source and license records too. Selected palettes can be evaluated independently of artwork, and a pack can ship with separately cleared images. [Omarchy license](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/LICENSE).

## T3 Code supplies a useful customization editor

The canonical project is `pingdotgg/t3code`. This research uses commit `b1e223e2b0d87124883b1410ab52dd6a1338e40d`.

Its Appearance page combines mode selection, theme cards, duplication, and JSON import and export. Users can select the light and dark halves independently. Its shared model includes semantic app colors and optional opposite-mode variants. That supports pairing modes, although Platform's main picker can avoid exposing independent halves until customization. [Appearance documentation](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/docs/user/appearance.md), [shared palette model](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/packages/shared/src/themePalettes.ts).

The editor starts with Background and Accent, generates related colors, and puts individual semantic roles under Advanced. It also lets users inspect an app area to find its color role. The first two ideas fit the initial Platform customization UI; the inspector can follow later. [Theme editor](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/apps/web/src/components/settings/ThemeEditorPanel.tsx).

There are two limits to the comparison. T3's VS Code importer maps workbench colors but does not import syntax `tokenColors`; its diff syntax still selects `pierre-light` or `pierre-dark`. Its optional sidebar artwork is not a wallpaper collection model. Platform therefore needs its own complete app, syntax, terminal, and wallpaper contract. [VS Code importer](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/apps/web/src/vscodeThemeImport.ts), [diff rendering](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/apps/web/src/lib/diffRendering.ts), [palette model](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/packages/shared/src/themePalettes.ts).

The repository uses MIT with a T3 Tools Inc. copyright notice. Any adapted code needs its notice retained and its color mapping rewritten for Platform's existing token roles. [T3 Code license](https://github.com/pingdotgg/t3code/blob/b1e223e2b0d87124883b1410ab52dd6a1338e40d/LICENSE).

## CodexThemes-App supplies artwork and library ideas

This research uses `NBchitu/CodexThemes-App` commit `d78e493bedef962b3bd1b73dfc58f83db5c60a52`. It is an independent community companion, explicitly unaffiliated with OpenAI. It applies an external visual layer over local CDP. This is evidence about the companion, not an official Codex theme API or the full customization contract of the closed-source app. [Project README](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/README.md).

A library card leads to an artwork detail view and Apply. Its controls include appearance, task artwork mode, and safe area. The pack model combines metadata, an image, role colors, and focal-point coordinates. It has no editor syntax field or authored light/dark pair. [Theme detail](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/src/components/ThemeDetail.tsx), [theme model](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/src/domain/theme.ts).

The renderer can derive colors from the artwork and adapt them to light or dark mode. Platform's first version should use authored colors with an optional guided generator. Image-derived themes can be evaluated later rather than assumed to preserve syntax or text contrast. [Renderer](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/resources/macos-engine/assets/renderer-inject.js).

The stricter `.codextheme` archive importer accepts a defined manifest and image layout and validates paths, links, image data, and size limits. Those checks are useful examples for Platform's own data-only importer. The CDP injection mechanism is unnecessary in an app that owns its renderer. [Archive importer](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/src-tauri/src/macos_bridge.rs).

The root code license is MIT, but the preset README explicitly identifies an artwork exception and links to a notice absent from the reviewed tree. Bundling its preset artwork remains unverified. Reuse the interaction ideas and validation approach; separately verify rights for any copied code, theme data, or image. [License](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/LICENSE), [preset terms](https://github.com/NBchitu/CodexThemes-App/blob/d78e493bedef962b3bd1b73dfc58f83db5c60a52/resources/macos-engine/presets/README.md).

## Current Platform behavior explains the confusion

These are source observations at the research baseline, not findings about the original author's intent. Plan 115 has since replaced the palette rows: `workbench.palette` is a palette id, palettes are data resolved into one `<style>` element, the terminal takes typed colors, and the TUI reads the shared palette instead of scraping CSS.

The existing [roadmap](../PLAN.md) records three constraints: one semantic settings mutation path, transient preview with commit handoff, and no disk reads inside `ghostty-webgpu`. Ghostty configuration inheritance was explicitly dropped. Omarchy theme import does not reopen that work.

Local logs were available only through 2026-09-09. The recent filtered settings events do not measure theme-switch paint behavior. A future implementation needs a fresh browser control and correlated appearance application evidence.
