# t1code: an OpenTUI + React front end bolted onto T3Code (deep read)

Repo: `/work/projects/platform/references/t1code` (fork of `pingdotgg/t3code`, published as `@maria_rcks/t1code` v0.0.24).
Upstream reference: `/work/projects/platform/references/t3code` (v0.0.35, far ahead of the fork's baseline).

## 0. TL;DR

- The TUI is **one 17,407-line file**: `apps/tui/src/ui.tsx`. The `App` component runs from line 4110 to the end (~13,300 lines): 47 `useState`, 75 `useEffect`, 40 `useMemo`, 29 `useCallback`, 7 `useRef`, one `useKeyboard`. The JSX `return (` starts at line 11959, so ~7,850 lines of hooks/handlers followed by ~5,450 lines of JSX. Every other file in `apps/tui/src` is a small pure helper with a co-located Vitest file; there are **zero tests of the UI itself**.
- Sharing with the web app is done through a fork-created package, `packages/client-core` (14 modules, ~3,700 lines): the WebSocket transport, the `NativeApi` factory, `sessionLogic` (timeline/approval/plan derivation from the server read model), app-settings schema, slash commands, sidebar sort/status, and small helpers. The web app re-exports these through one-line shims (`apps/web/src/session-logic.ts` is literally `export * from "@t3tools/client-core/sessionLogic";`).
- **State strategy is identical in both front ends**: no client-side event application. On every `orchestration.domainEvent` push, the client re-fetches the entire `OrchestrationReadModel` snapshot (TUI: coalesced runner at `ui.tsx:4893-4924`, `4993-4996`; web: 100 ms trailing throttle at `apps/web/src/routes/__root.tsx:167-235`). `sessionLogic` then derives the timeline from `thread.activities` and `thread.messages`.
- Seams they cut: terminal drawer is **not a terminal emulator** (ANSI stripped, plain text rows, a one-line `<input>` that writes `${cmd}\r`); no streaming assistant text; no virtualization; no checkpoints/revert; no PR-thread dialog; no terminal context chips; no provider-skill chips; no drag-and-drop; single terminal per thread; `terminal.resize` is never called; tree-sitter grammars are **downloaded from GitHub at runtime** for code-block highlighting.
- Cost of the seams: a monolithic component that cannot be tested, a permanent upstream-parity treadmill documented in `.plans/upstream-t3code-parity.md` (25 KB of "slices" and a list of 7 remaining groups), and a bespoke server launch mode (`--mode tui`) that upstream does not have.

## 1. Provenance: what the fork changed vs upstream

### 1.1 Git history is unavailable

Both clones are shallow with a single commit (`git rev-parse --is-shallow-repository` → `true`, `git rev-list --count HEAD` → `1` in both). The fork's plan file names its baseline (`b3bca04c`) and parity source (`b83e9c95`), but neither commit exists in our `t3code` clone (HEAD `c8aba258`, v0.0.35). So the "diff against upstream" is a **directory diff that mostly measures upstream drift**, not fork changes. Numbers, for the record:

### 1.2 What is verifiably fork-specific

- `apps/tui/**` — the whole TUI (does not exist upstream).
- `packages/client-core/**` — does not exist upstream. Upstream instead has `packages/client-runtime` (README at `t3code/packages/client-runtime/README.md`: subpaths `authorization`, `connection`, `environment`, `errors`, `operations`, `platform`, `relay`, `rpc`, `state/<domain>`), imported by 161 web files and 112 mobile files. The fork's plan file item 7 explicitly lists "`packages/client-runtime` replacement/adaptation while preserving TUI compatibility" as _unfinished_.
- `apps/server/src/main.ts` — `Flag.choice("mode", ["web", "desktop", "tui"])` at line 415; `--home-dir` at 430; `--auto-bootstrap-project-from-cwd` at 453. `grep -rn '"tui"' t3code/apps/server/src` returns nothing: **the `tui` server mode is a fork invention**. In `tui` mode the server defaults to `DEFAULT_PORT` instead of scanning (`main.ts:202-206`), binds `127.0.0.1` (`main.ts:282`), and defaults `--no-browser` on (`main.ts:241`). Auto-bootstrap defaults to `mode === "web"` (`main.ts:259`) so the TUI passes the flag explicitly.
- `packages/contracts/src/ws.ts` (fork-only; upstream has `rpc.ts`). Fork protocol: request `{ id, body: { _tag: "<method>", ...params } }`, push `{ type: "push", channel, data }` (`client-core/src/wsTransport.ts:60-66, 105-136, 262-299`). Upstream moved to Effect RPC. This is the single biggest divergence for a future rebase.
- `apps/web/src/appSettings.ts` (fork-only) — a thin wrapper that reads `AppSettingsSchema` from client-core via `useLocalStorage` (lines 38-62).
- Tooling: Bun workspaces + turbo (`package.json`, `turbo.json`) instead of upstream's pnpm + `vite-plus` (`vp`). Root scripts add `dev:tui`, `dev:tui:headless`, `start:tui`, `build:tui`.
- Docs: `AGENTS.md` (says `apps/tui` is "the main product surface"; "assume they mean the TUI"), `README.md`, `TODO.md` (scroll-to-bottom on send, thread archiving, project sort, message queueing — all still open), `KEYBINDINGS.md` and `REMOTE.md` are inherited upstream docs that still describe the _web_ app (`~/.t3/keybindings.json`, `--mode <web|desktop>`), not the TUI.

### 1.3 The parity treadmill

`.plans/upstream-t3code-parity.md` is 423 lines. Lines 20-362 list ~120 "completed slices", most of them one-commit backports ("align with upstream `xxxx`"). Lines 364-414 list seven remaining groups: Effect 4 catalog migration, ACP/Cursor providers, terminal/shell state parity, pluggable VCS, settings route split + keybindings editor, hosted pairing / SSH / Tailscale, desktop refactor, oxlint plugin, and the client-runtime replacement. Line 6-8 states the rule: "Upstream parity work must apply upstream behavior without removing those fork surfaces unless a replacement has been implemented and wired." This is the cost of forking a fast-moving upstream and adding a second front end that consumes internals instead of a stable contract.

## 2. Runtime, packaging, and how the server is bundled

### 2.1 Entry binary

`apps/tui/bin/t1code.js` (43 lines): if `process.versions.bun` is undefined, re-spawn `bun dist/index.mjs` with inherited stdio (lines 13-38); ENOENT prints "t1code requires Bun on your PATH". Both `t1` and `t1code` bins map to it (`package.json:16-19`). Engines: `bun >=1.3.9`.

### 2.2 Build

`apps/tui/scripts/build-runtime.mjs`: `bun build src/index.tsx --target bun --format esm --outdir dist --entry-naming [name].mjs` (lines 21-45); prepends `#!/usr/bin/env bun`; rewrites the native specifier `@opentui/core-${platform}-${arch}/index.ts` → without `/index.ts` (lines 51-54) so Bun resolves the optional platform packages at runtime; copies `parser.worker.js(.map)` from `@opentui/core` into `dist/` (lines 60-70) — the tree-sitter worker must sit next to the bundle.

`apps/tui/scripts/bundle-server-dist.mjs`: runs `bun run build` in `apps/server`, then re-bundles `apps/server/src/index.ts` with `bun build --target=node --format=esm --splitting --packages=bundle --external node-pty --external ws` into `apps/tui/dist/server` (lines 88-104); copies the built web client (`apps/server/dist/client`) into `dist/server/client` (105-107); copies `node-pty` runtime files (`lib`, `prebuilds`, `typings`, `package.json`) into `dist/server/node_modules/node-pty` (108-114). So the npm package ships **TUI + server + web app + PTY binaries**. `prepare-package-json.mjs` strips workspace devDependencies for publish; `restore-package-json.mjs` restores after `postpack`.

`tsdown.config.ts` exists but is not what `build` runs (`package.json:29` uses the two scripts above).

### 2.3 Publishing

`.github/workflows/publish-npm.yml`: on push to `main` → `npm publish --tag dev` with version `X.Y.Z-dev.<run>.<attempt>.<sha>`; on `v*` tag → `npm publish`. Gates are fmt/lint/typecheck only; **no tests run in CI**.

### 2.4 Dev loop

`scripts/dev-tui.ts` (root): reserves a loopback port (line 89-108), spawns `bun apps/server/src/index.ts --mode tui --auto-bootstrap-project-from-cwd --host --port --auth-token <random 16 bytes hex> --home-dir ~/.t1 --no-browser` (203-224), logs stdout/stderr to `~/.config/t1code/tui.log`, polls TCP until ready (10 s), then spawns `bun --silent --watch run apps/tui/src/index.tsx` with `T1CODE_TUI_ATTACH_ONLY=1` plus host/port/token env (248-260). All `T1CODE_*`/`T3CODE_*` env is stripped before spawning the server (`stripReservedLaunchEnv`, line 80-84).

## 3. OpenTUI + React setup

### 3.1 Renderer configuration (`apps/tui/src/index.tsx`)

```ts
const renderer = await createCliRenderer({
  exitOnCtrlC: false, // line 89
  screenMode: shouldUseAlternateScreen() ? 'alternate-screen' : 'main-screen', // 90
  useMouse: shouldUseMouse(), // 91 (default true)
  enableMouseMovement: shouldEnableMouseMovement(), // 92 (default false)
  useKittyKeyboard: shouldUseKittyKeyboard() ? { events: true } : null, // 93
  ...(!shouldDeferInitialBackground ? { backgroundColor: initialTheme.palette.canvas } : {}),
})
```

Kitty keyboard protocol is auto-enabled when `TERM_PROGRAM/TERM/COLORTERM` contains ghostty/kitty/wezterm/iterm (lines 31-36), overridable with `T1CODE_USE_KITTY_KEYBOARD`. Other env knobs: `T1CODE_USE_ALTERNATE_SCREEN`, `T1CODE_USE_MOUSE`, `T1CODE_ENABLE_MOUSE_MOVEMENT`.

Theme bootstrapping: reads `prefs.json` (line 81), and if the theme is `system` or the TUI theme is `terminal-match` it defers the background, queries the terminal palette with `renderer.getPalette({ size: 16 })` (`rendererTheme.ts:41-63`, OSC 4/10/11 under the hood), resolves light/dark from it (`theme.ts` `resolveTerminalThemeMode`), then `renderer.setBackgroundColor(...)` (line 106). `renderer.themeMode` is also read (line 96).

Root: `createRoot(renderer).render(<App renderer={renderer} .../>)` (107-121). SIGINT does **not** exit: it bumps `interruptRequestToken` and re-renders so the app can show its own quit prompt (146-152). SIGTERM/SIGHUP/uncaughtException/unhandledRejection call `shutdown()` which unmounts, destroys the renderer, and `process.exit`s after 50 ms (123-143).

### 3.2 Headless mode (`T1CODE_HEADLESS=1`, `index.tsx:50-76`)

Uses `createTestRenderer({ width, height, kittyKeyboard: true })` from `@opentui/core/testing`, renders `<App>`, waits `T1CODE_HEADLESS_TIMEOUT_MS` (default 1500), calls `renderOnce()` and `captureCharFrame()`, writes the frame to `T1CODE_HEADLESS_FRAME_PATH` (default `~/.config/t1code/headless-frame.txt`), exits 0. Env passthrough is declared in `turbo.json:15-20`. This is a **screenshot tool for agents/humans, not a test harness**: nothing in CI calls it and no test file imports `@opentui/core/testing` (only `index.tsx` does). Note the root `package.json:36` script uses `T3CODE_HEADLESS=1` while `index.tsx:50` checks `T1CODE_HEADLESS` — the root script is broken; `apps/tui/package.json:28` uses the correct name.

### 3.3 JSX and dependencies

`apps/tui/tsconfig.json`: `"jsx": "react-jsx", "jsxImportSource": "@opentui/react"`, `lib` includes DOM (needed because client-core's tsconfig also declares DOM libs).

Dependencies (`apps/tui/package.json:41-49`): `@opentui/core ^0.2.7`, `@opentui/react ^0.2.7`, `effect`, `react ^19`, `react-devtools-core ^7.0.1`, `web-tree-sitter 0.25.10`, `ws ^8.18`. Six `@opentui/core-<platform>-<arch>` optional deps pinned to 0.2.7.

- `react-devtools-core` is **not referenced anywhere in `apps/tui/src`** (grep returns nothing). It is a **peerDependency of `@opentui/react`** (`bun.lock:683`: `"peerDependencies": { "react": ">=19.2.0", "react-devtools-core": "^7.0.1", "ws": "^8.18.0" }`), so they added it to satisfy the peer. Same story for `ws`: it's OpenTUI's peer, and the TUI's `WsTransport` uses `globalThis.WebSocket` (Bun's built-in) — `wsTransport.ts:75-81`.
- `web-tree-sitter 0.25.10` is a **peerDependency of `@opentui/core`** (`bun.lock:669`) and powers the `<code>`, `<diff>` and `<markdown>` renderables' syntax highlighting. Not imported directly by TUI code.

OpenTUI elements actually used in `ui.tsx` (counted): `<box>` ×247, `<text>` ×214, `<input>` ×20, `<scrollbox>` ×7, `<markdown>` ×2, `<textarea>` ×1, `<diff>` ×1, `<code>` ×1. No `<select>`, `<tab-select>`, `<ascii-font>`; every menu/list/popup is hand-built from `box`/`text` with `onMouseDown` (46 mouse handlers).

`node_modules` is not installed in the reference clone, so OpenTUI internals were not inspected; the `opencode` reference uses `@opentui/solid`, not `@opentui/react`.

## 4. Server connection and auth token flow

### 4.1 Two launch modes

`apps/tui/src/serverSupervisor.ts`:

- **Managed** (`startServerSupervisor`, lines 226-361): picks the server entry (`resolveServerEntry`, 212-224): bundled `dist/server/index.js` if present, else `apps/server/dist/index.mjs` under `NODE_ENV=production`, else `bun run apps/server/src/index.ts`. Spawns with `--mode tui --auto-bootstrap-project-from-cwd --host <h> --port <p> --auth-token <t> --home-dir <homeDir> --no-browser` (256-271), `cwd: process.cwd()` (so the CWD becomes the bootstrapped project), env scrubbed of `T1CODE_*`/`T3CODE_*` (153-157). Token is `randomBytes(16).toString("hex")` unless given (238). Readiness = TCP connect poll every 100 ms up to 10 s (181-210). On child exit it restarts after 750 ms unless stopped or a fatal startup error (EACCES/EPERM regex, 67-77) was seen before readiness (302-319). Dependencies (`spawnImpl`, `reservePort`, `waitUntilReady`, timers, env) are injectable (53-65) — this is why `serverSupervisor.test.ts` can run without spawning anything.
- **Attach-only** (`resolveAttachedServerConnection`, 127-151): `T1CODE_TUI_ATTACH_ONLY=1` + `T1CODE_HOST` + `T1CODE_PORT` + `T1CODE_AUTH_TOKEN`; throws if port/token missing. This is the only "remote" story: the Connections settings view builds `env T1CODE_TUI_ATTACH_ONLY='1' T1CODE_HOST=... T1CODE_PORT=... T1CODE_AUTH_TOKEN=... t1code` (`connectionsPanel.ts:29-37`) from `server.getAdvertisedEndpoints`, masks the token for preview (39-45), and the "Remote environments" settings row just says to set those env vars (`ui.tsx:14962-14968`).

### 4.2 Token transport and validation

`buildServerWsUrl` → `ws://host:port/?token=<encoded>` (`serverSupervisor.ts:123-125`). The server validates on HTTP upgrade only: `apps/server/src/wsServer.ts:1131-1148` parses `?token=` and rejects with 401 if it mismatches `authToken`. No per-message auth, no TLS. The token lives in the process argv of the server child (visible in `ps`), which upstream's `--bootstrap-fd` envelope was designed to avoid (`REMOTE.md`), but the TUI does not use it.

### 4.3 Client wiring inside `App` (`ui.tsx:4845-5045`)

1. `resolveAttachedServerConnection()` or `await startServerSupervisor({...})` (4845-4869).
2. `new WsTransport({ url, onWarning })` (4872-4875); `createTransportNativeApi({ transport })` (4878) — no dialogs/shell/contextMenu hooks are passed, so `api.dialogs.pickFolder` returns `null`, `confirm` returns `false`, and `shell.openExternal` throws (`client-core/src/nativeApi.ts:70-101`). The TUI uses its own `openExternalUrl` (`openExternal.ts`) instead.
3. `refresh = createCoalescedRefreshRunner(...)` requests `ORCHESTRATION_WS_METHODS.getSnapshot` with a 5 s timeout, `setSnapshot`, retries after 1 s on failure and flips status to "Disconnected" after 3 failures (4893-4924).
4. Loads `server.getConfig()` and `server.getSettings()` (4927-4965).
5. `onServerWelcome` → applies `bootstrapProjectId/bootstrapThreadId` selection once (4968-4991); `onDomainEvent` → `refresh("domain-event")` (4993-4996); `onServerConfigUpdated` merges `issues/providers/providerInstances` (4997-5010); `terminal.onEvent` → `applyTerminalEventToSession` (5011-5018).
6. Cleanup disposes transport and stops the server (5020-5029).

### 4.4 `WsTransport` (`client-core/src/wsTransport.ts`)

Request timeout 60 s (line 52; `timeoutMs: null` for long git/source-control ops in `nativeApi.ts:106,138,140`), reconnect backoff `[500, 1000, 2000, 4000, 8000]` ms (53), outbound queue while not open (301-311), `latestPushByChannel` replay for `serverWelcome`/`serverConfigUpdated` (169-172, used by `nativeApi.ts:179,189`), stale-socket guards (`this.ws !== ws`, 206-244), Effect Schema decode of every inbound frame (`decodeUnknownJsonResult(WsResponseSchema)`, 54, 263-267). Listener exceptions are swallowed (274-278).

## 5. State model: server read model + derive-everything

There is no client store in the TUI. `snapshot: OrchestrationReadModel | null` (`ui.tsx:4131`) is the source of truth; `OrchestrationReadModel = { snapshotSequence, projects, threads, updatedAt }` (`packages/contracts/src/orchestration.ts:347-352`). Everything else is derived per render:

- `groupThreadsByProject` (`ui.tsx:2926`), `sortProjectsForSidebar`/`sortThreadsForSidebar` (client-core `sidebarSort.ts`), `resolveThreadStatusPill`/`resolveProjectStatusIndicator` (client-core `sidebarStatus.ts`).
- `deriveTimelineEntries` (`sessionLogic.ts:1047`) → `TimelineEntry = message | proposed-plan | work` (88-106); `deriveWorkLogEntries` (521-1037, ~500 lines mapping `OrchestrationThreadActivity` kinds to `WorkLogEntry { label, detail, command, changedFiles, tone, itemType }`); `derivePendingApprovals` (246), `derivePendingUserInputs` (351), `deriveActivePlanState` (400), `findLatestProposedPlan` (461), `deriveLatestContextWindowSnapshot` (`contextWindow.ts`).
- `derivePendingUserInputProgress` (`pendingUserInput.ts:74-102`) drives the multi-question answer UI; `resolvePlanFollowUpSubmission` (`proposedPlan.ts:68-84`) decides whether a send is a plan follow-up (`interactionMode: "plan"`) or "PLEASE IMPLEMENT THIS PLAN:" (`interactionMode: "default"`).

The web app derives from the same functions; the difference is that the web has a zustand store (`apps/web/src/store.ts`, `syncServerReadModel`) plus TanStack Query for git/provider data, while the TUI keeps 47 `useState`s in one component and `useEffect`-syncs refs (`ui.tsx:5048-5054`).

Client-local persistence: `~/.config/t1code/prefs.json` (`prefs.ts:45-74`): theme id, selected project/thread, expanded projects, locally-unread threads, last-visited timestamps, draft threads by project, composer drafts by thread (including base64 image data URLs), main view, draft provider/instance/model/options/runtime/interaction mode, diff open/view, and the whole `appSettings` blob (the web keeps the same `AppSettings` in `localStorage` under `t3code:app-settings:v1`, `appSettings.ts:16`). Prefs are re-written from a `useEffect` on every change (`ui.tsx:5057+`); no schema validation on read (`prefs.ts:76-84` is `JSON.parse` in a try/catch).

Orchestration commands dispatched from the TUI (all through `dispatch()` at `ui.tsx:8506-8510` → `api.orchestration.dispatchCommand`): `project.create`, `project.meta.update`, `project.delete`, `thread.create`, `thread.meta.update`, `thread.archive`, `thread.unarchive`, `thread.delete`, `thread.turn.start`, `thread.turn.interrupt`, `thread.session.stop`, `thread.approval.respond`, `thread.user-input.respond`. Other `NativeApi` calls: `git.status/pull/listBranches/createWorktree/checkout/runStackedAction/onActionProgress`, `terminal.open/write/restart/close/clear`, `server.refreshProviders/updateProvider/getTraceDiagnostics/getProcessDiagnostics/signalProcess/discoverSourceControl/getAdvertisedEndpoints`, `sourceControl.cloneRepository/publishRepository`, `shell.openInEditor`, `orchestration.getFullThreadDiff`. **Never called**: `terminal.resize`, `git.init/createBranch/removeWorktree/resolvePullRequest/preparePullRequestThread`, `orchestration.getTurnDiff/replayEvents`, `server.upsertKeybinding/updateSettings` (settings are patched via `updateServerSettings` — check `ui.tsx:4571`), `projects.writeFile`.

## 6. Screen / route structure

No router. Navigation is three union-typed `useState`s (`ui.tsx:268-296`):

- `MainView`: `thread | settings | keybindings | providers | source-control | scripts | connections | diagnostics | archive`. `SETTINGS_NAV_ITEMS` (`ui.tsx:488-505`) gives each an icon and label; `openMainView()` (8612-8618) sets `focusArea = "settings"`; `returnToThreadView()` (8620-8625).
- `FocusArea`: `projects | threads | controls | composer | timeline | terminal | diff | settings`. Focus is fully manual: each `<scrollbox>`/`<input>`/`<textarea>` receives `focused={focusArea === "..."}` and the app calls `.focus()` on refs in `setTimeout(..., 0)` after state changes (e.g. 8677-8679, 8696-8698).
- `OverlayMenu`: `command-palette | model | traits | settings-select | sidebar-sort | git-actions | composer-env | composer-branch`, plus separate state for `confirmDialog`, `renameThreadDialog`, `imagePreview`, `sidebarContextMenu`, `projectPathPromptOpen`, `sidebarOverlayOpen`. Overlays are `position: "absolute"` boxes with `zIndex` (e.g. sidebar overlay at 120/130, `ui.tsx:11985-12010`), positioned by `resolvePopupPosition` (2850).

Layout (`ui.tsx:11959-12060`): root `box` row, full width/height, `backgroundColor: PALETTE.canvas`; left sidebar `width: TUI_SIDEBAR_WIDTH` (34 cols, `responsiveLayout.ts:1`) with `border: ["right"]`; main column. `resolveTuiResponsiveLayout` (`responsiveLayout.ts:27-64`) collapses the sidebar when the main panel would be ≤ 44 cols, offers a toggle at ≤ 56, hides composer labels below 44/62/72 cols, hides the header project badge below 144 cols. Below the collapse threshold the sidebar becomes an overlay (`showSidebarOverlay`).

Main-column contents, in order (`ui.tsx:12400-16600`): header (title, project badge, git actions, terminal/diff toggles), then one of `settings-family views` | `full diff view` (15074) | `timeline scrollbox` (15212, `stickyScroll stickyStart="bottom"`), then optional plan panel (`PlanDetailsPanel`, 3645), optional terminal drawer (15684), then the composer panel with pending-input question UI (15950+), attachments/mentions pills, the `<textarea>` (16009), and a footer toolbar (provider/model/traits/env/branch controls + send button).

## 8. Sidebar / thread list

## 9. Message rendering

`MessageMarkdown` (`ui.tsx:2227-2377`): `parseMessageMarkdownSegments` (`messageMarkdown.ts:54-102`) splits on fences (3+ backticks or tildes, indented ≤3); markdown segments go to `<markdown content syntaxStyle={MESSAGE_MARKDOWN_SYNTAX} conceal>`; code segments render a language label + `<code content filetype syntaxStyle wrapMode="char">` with `udiff/unified-diff` mapped to the `diff` filetype (`messageMarkdown.ts:104-122`) and a diff-specific `SyntaxStyle` (`buildDiffSyntax` 934). Syntax styles are rebuilt from the palette (`buildMessageMarkdownSyntax` 899-932: heading/link/code/list/emphasis captures). User messages are right-aligned bubbles of width `resolveUserMessageBubbleWidth` (`messageLayout.ts`), assistant messages fill the width; mention tokens are stripped from user text and shown as pills (`stripMentionTokensFromText` 1608, `MessageMentions` 2158); attachments become clickable chips (`MessageAttachments` 2187) that open the kitty preview. Work entries are one-line rows with an icon (`workEntryIcons.ts`), heading (`toolWorkEntryHeading` 2514), truncated preview (`ui.tsx:15460-15475`). Timestamps use `Intl.DateTimeFormat` per `timestampFormat` (1305-1325).

Theme is applied by **mutating module-level globals**: `const PALETTE: TuiPalette = { ...DEFAULT_TUI_THEME.palette }` and `let ACTIVE_TUI_THEME` (`ui.tsx:676-677`), with `MESSAGE_MARKDOWN_SYNTAX`/`DIFF_SYNTAX`/`CODE_BLOCK_SYNTAX` rebuilt on theme change. This is why `App` cannot be instantiated twice and why the theme is not testable in isolation.

## 10. Composer

- `<textarea key={composerResetKey} ref={composerRef} focused={composerIsFocused} initialValue={composer} onKeyDown=...>` (`ui.tsx:16009-16200+`). The textarea is **uncontrolled**: value is read back via `composerRef.current?.plainText` (`readComposerValue`) and mirrored into `composerValueRef` through a deferred sync (`composerSync.ts`); resetting means bumping `composerResetKey` to remount.
- `onKeyDown` chain (16014-16200): image-paste-in-flight guard → Ctrl+C clears draft or requests exit (`keyboardBehavior.ts:122-136`) → double-Delete removes last attachment/mention → Ctrl+Y attaches clipboard image → slash menu navigation (↑/↓/Ctrl+J/K/Tab/Enter) → path-suggestion navigation → Enter sends, Shift+Enter newline.
- `sendPrompt` (`ui.tsx:10080-10400`): standalone `/plan`|`/default` → interaction mode; slash command → `handleSlashCommand`; pending approval blocks; pending user input advances; otherwise builds `createModelSelection(instanceId, model, optionSelections)` (from `@t3tools/shared/model`), prefixes `@path` mentions, resolves inline image paths to base64 data URLs (`resolveComposerSubmission`), auto-creates a project from `process.cwd()` if none (10159-10163), pushes a `PendingSendPreview` for optimistic display (`SEND_PLACEHOLDER_MIN_DURATION_MS`), persists thread settings (`thread.meta.update`) and dispatches `thread.turn.start` with `{ messageId, role: "user", text, attachments }` (10192, 10350). ## 11. Terminal drawer: not an emulator

`terminalDrawer.ts` (125 lines) is the whole model:

- `TuiTerminalSession { terminalId, cwd, status, pid, output: string, exitCode, exitSignal, error, hasRunningSubprocess, updatedAt }` (6-17).
- `terminalSessionFromSnapshot` strips ANSI (`TERMINAL_ANSI_SEQUENCE_PATTERN`, 19-22) from `snapshot.history` and trims to the last 60,000 chars (`TUI_TERMINAL_MAX_OUTPUT_CHARS`, 4). `applyTerminalEventToSession` appends stripped `output` events, handles `exited/error/cleared/started/restarted` (48-109).
- Rendering (`ui.tsx:15684-15820`): a bordered box with header ("Terminal", `formatTerminalStatus`, cwd), New/Clear/✕ buttons, an optional warning line, a `<scrollbox height={12}>` of `<text>` rows (last `max(48, 20)` lines, 5225), and a `$` prompt `<input>` whose Enter calls `submitTerminalInput` → `api.terminal.write({ data: `${value}\r` })` (8735-8760). Opening calls `api.terminal.open({ cwd, cols: clamp(mainPanelColumns-6, 20..200), rows: 12, env: { T3CODE_PROJECT_ROOT } })` (8648-8672).
- Consequences: no cursor, no colors, no TUI programs (vim/htop will corrupt), no resize on window change, no scrollback beyond 60 KB, no per-key forwarding (only line-buffered commands), one terminal per thread, and `terminal.resize` is never invoked. Keyboard: Esc leaves the drawer (8047-8054); ↑/↓ are swallowed (8055-8057).

The web app uses `@xterm/xterm` + `FitAddon` (`apps/web/src/components/ThreadTerminalDrawer.tsx:1-4, 275`), 1,219 lines, with link detection (`terminal-links.ts`) and activity tracking (`terminalActivity.ts`).

## 13. Keybinding handling

Two layers:

1. **Server-resolved keybindings** (`ResolvedKeybindingsConfig` from `server.getConfig().keybindings`, contract in `packages/contracts/src/keybindings.ts`): `resolveTuiShortcutCommand(event, keybindings, { context })` (`apps/tui/src/keybindings.ts:112-128`) walks rules **last-to-first** (upstream precedence rule), evaluates the parsed `whenAst` (`identifier | not | and | or`, 89-102) against `{ terminalFocus, terminalOpen, modelPickerOpen }` (22-27), and matches the shortcut with `mod` → meta on darwin / ctrl elsewhere (65-77). A subtlety: raw control characters (sequence `\x01`-`\x1a`) are mapped back to letters (`controlKeyFromSequence`, 38-43) for terminals without the kitty protocol. Commands recognized in the TUI: `commandPalette.toggle`, `modelPicker.toggle`, `modelPicker.jump.N`, `terminal.toggle/new/close/split`, `thread.jump.N`, `thread.previous/next` (`ui.tsx:7982-8085`). Web-only commands like `chat.new`, `editor.openFavorite`, `script.{id}.run` are ignored.
2. **Hard-coded TUI keys** in the single `useKeyboard` handler (`ui.tsx:7819-8300+`): a priority chain — confirm dialog (Esc/Ctrl+C/Enter) → rename dialog → image preview → sidebar overlay → digit shortcuts for pending questions → project-path prompt → command palette → overlay Esc → context-menu Esc → Ctrl+C quit prompt (only when nothing dismissible is open and the composer is unfocused) → context-menu navigation → shortcut commands → terminal focus keys → thread jump/traverse → model-menu typeahead → ... . Every keypress is also logged to `tui.log` (`logger.log("ui.key", ...)`, 7835-7843). Element-level `onKeyDown` on `<textarea>`/`<input>` runs in addition to this global handler, and the two coordinate through `key.preventDefault()`.

There is no chord support, no rebinding UI, and `KEYBINDINGS.md` still documents the web app's file. The Keybindings settings view renders the static `KEYBINDING_GUIDE_SECTIONS` (`keyboardBehavior.ts:12-120`).

## 17. The seams they cut, and what each cost

1. **One component instead of a feature tree.** Cutting the web's component structure (ChatView 4,145 lines, Sidebar 1,821, DiffPanel 706, settings route 1,063, ThreadTerminalDrawer 1,219 in the fork's web) into one `App` with 190+ hooks means: every keypress, every pulse tick, every snapshot refresh re-renders everything; `useEffect` ordering is the only "architecture"; nothing can be unit-tested; module-level `PALETTE` mutation forbids a second instance. They compensated by extracting every _pure_ decision into a tested helper file (good), but all wiring remains untested.
2. **Snapshot refetch instead of event application.** Cheap to build (no reducer, no reconciliation) and shared with the web; costs a full `getSnapshot` round-trip per domain event (coalesced), meaning streaming tokens can never render incrementally and a large workspace (many threads with full `messages`/`activities` arrays) grows per-event payload without bound. The `enableAssistantStreaming` setting is essentially inert in the TUI.
3. **Text log instead of terminal emulation.** Avoided embedding a VT parser (OpenTUI 0.2.7 has no terminal widget); cost is every interactive shell feature. They also left `terminal.split` and multiple terminals as "not available yet" strings.
4. **Runtime-fetched grammars.** Avoided bundling ~26 WASM files; cost is a network dependency for syntax highlighting and unpinned `master` queries.
5. **Custom server mode + bundling the server into the npm package.** Made `bunx @maria_rcks/t1code` a one-command experience; cost is a fork-specific `--mode tui` in the server, a 100+-line bundling script that knows about Bun's store layout for `node-pty`, and Bun as a hard runtime requirement.
6. **Attach-only env vars instead of a connection model.** Got remote attach for free; cost is no connection registry, no reconnect UX beyond the transport's backoff, no environment switching (upstream's `client-runtime/connection` is 4,000+ lines for that reason) and a token in argv.
7. **`client-core` as an extraction of what the web happened to have as pure modules.** Sharing was cheap because upstream already kept `session-logic.ts` etc. framework-free; but the package mirrors web module boundaries rather than a designed client SDK, declares DOM libs, and its `NativeApi` shape still includes desktop concepts (`dialogs`, `contextMenu`) the TUI stubs out. Upstream then replaced the whole layer (`client-runtime`), leaving the fork to carry both.
8. **Keyboard model.** A single ordered `if` chain plus per-element `onKeyDown` is easy to reason about at 200 lines and impossible at 500; focus is manual state with `setTimeout(focus, 0)` sprinkled at ~15 sites.

## 18. What is worth reusing or stealing for our TUI

- **Managed-server supervisor with injectable spawn/port/readiness** (`serverSupervisor.ts`) — the structure (restart-on-exit, fatal-startup detection, attach-only escape hatch, reserved loopback port, env scrubbing) maps directly onto an Elysia server child; the tests show how to cover it without spawning.
- **Headless frame capture** (`index.tsx:50-76`) — trivial to replicate with `createTestRenderer`/`captureCharFrame`; make it a _test fixture_ rather than an env flag.
- **Keybinding resolution against a server-provided rule list with `when` AST** (`keybindings.ts`) — a small, tested pattern; our `keymap/` command registry could produce the same `ResolvedKeybindingsConfig` shape for the TUI.
- **Pure-helper-per-decision + co-located test** discipline (e.g. `responsiveLayout.ts`, `sidebarContextMenu.ts`, `threadSelection.ts`) — the one thing that kept the monolith maintainable.
- **Platform helpers**: `openExternal.ts` (xdg-open/gio/wslview/open/cmd), `clipboardText.ts` (wl-copy/xclip/xsel/pbcopy/clip.exe), `clipboardImage.ts` (wl-paste/xclip/inline Swift for macOS), `terminalImages.ts` (kitty graphics protocol via raw `writeOut`, chunked base64, capability detection from `renderer.capabilities.kitty_graphics`).
- **Diff normalization for OpenTUI `<diff>`** (`normalizePatchForOpenTuiDiff`) — needed if we render git patches with that element.
- **Fence splitting for markdown + `<code>`** (`messageMarkdown.ts`) — until OpenTUI's `<markdown>` highlights fences natively.
- **Responsive breakpoints in columns** (`responsiveLayout.ts`) — sidebar 34 cols, collapse at ≤44 main cols, etc.

What _not_ to copy: the single-file `App`; module-level palette mutation; prefs-as-unvalidated-JSON; snapshot-per-event without an incremental path; the text-log terminal if we can drive a real PTY renderer; runtime grammar downloads.
