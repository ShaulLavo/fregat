# Native Mac Client — Plan of Plans

**Direction (settled 2026-08-28):** a native Swift macOS client as a second frontend. The web app stays for cross-platform. The Bun server stays the brain (fs, git, LSP proxy, PTYs, settings); the native app is a client of the same contracts. **Editor-first is the strategy and the gate:** until the from-scratch native editor matches or beats the web editor's measured standard, there is no app. Shell and platform FE grow around a proven editor, not before it.

**Reference architecture (settled 2026-08-28): the ghostty model.** Own every pixel of the hot surface; be ruthlessly native everywhere else. The editor surface is one custom owner-drawn `NSView` (CoreText + augmented line tree; Metal later only if the bench demands it) that still speaks the OS protocols — `NSTextInputClient` for IME, `NSAccessibility` — the way ghostty's terminal surface does. Around it: AppKit skeleton (window, splits, responder chain — CodeEdit tried SwiftUI at the window root and documentedly reverted), SwiftUI leaves for panels/settings/inspectors, native menus and glass. Never `NSTextView`, never TextKit for the editor. The terminal pane later embeds libghostty — the same model, applied twice.

**Port-first doctrine (settled 2026-08-28):** wherever the web editor (`editor/`) already solved a problem, the native plan starts by porting that design **1:1** — data structures, algorithms, invariants, and its tests as the spec — then diverges deliberately: cleaner code, fixing known mistakes, and Swift-appropriate idioms (value types, `Sendable` snapshots, ARC-aware allocation) are encouraged; _novel design_ is reserved for problems the web editor never had (CoreText typesetting, `NSTextInputClient`, `NSAccessibility`, AppKit integration). Every plan doc names what it ports vs what it designs fresh. First instance: the piece-table treap (see `native-editor-internals-research.md` directive 1).

**Gate definition:** core editing (typing, scrolling, selection, undo) + tree-sitter highlighting + LSP diagnostics/completion via the server proxy, at or above the web editor's numbers on the same machine. Feature parity (minimap, diff, decode animation, scope lines…) accretes after the gate, not before.

## Step 0 — toolchain (done)

Done 2026-08-28: **Xcode 26.6 (Swift 6.3.3, macOS 26.5 SDK)** is installed and selected, and `swift build`/`swift test`/`swift run -c release EditorBench` all pass on Apple M1 / macOS 26.4. Xcode 27 is in beta for macOS 27 "Golden Gate" (~Sept 2026). The one-time selection was:

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer && xcodebuild -runFirstLaunch
```

`apps/mac` is scaffolded (SwiftPM: `EditorCore` lib, `EditorBench` + `MacApp` executables, swift-testing tests) and is not part of the bun/turbo workspace — it has no `package.json` on purpose.

**Scaffolding approach (validated by research, Aug 2026):** pure SwiftPM is the state of the art for a solo CLI-first dev-only Mac app — no `.xcodeproj` in git, `swift build`/`run`/`test` all CLI-native, SourceKit-LSP works in any editor. `swift run MacApp` shows a real window without a bundle; when a real `.app` bundle is eventually wanted, [swift-bundler](https://github.com/stackotter/swift-bundler) (actively maintained) or a 15-line copy script does it, and unsigned `xcodebuild` works with `CODE_SIGNING_ALLOWED=NO`. XcodeGen (still maintained) only if entitlements/Instruments schemes ever force a project file; Tuist is overkill for one app.

### B3R — recover large-document mount performance

**Status:** not started. This repair was deliberately separated from the measurement session.

Preserve anchor-backed inline replacements while removing the large-document mount overhead introduced by `cca9a0b3`. Start in the inline-mapping and row-projection paths added by that commit. The exit criterion is a same-session, interleaved `virtualization.mount.large` ratio no worse than 1.10× its parent/control, with mounted-row and long-line invariants unchanged. Record the result as dated JSON.

The systemic decision is now **yes**: plan 6 should check in dated JSON for both web and native benches. `native-bench-harness.md` §10 defines the minimal record, including commit, runtime/browser flags, corpus, calibration, metrics, and an error state. That record would have rejected B2's uncalibrated sample, located B3 in the week it landed, and made B4's broken run visible.

## Open decisions (talk about these)

- **App identity**: name and bundle id for `MacApp` when it becomes a real `.app` bundle.
- ~~**Deployment target**~~ decided: macOS 26 only (`.macOS(.v26)` in `Package.swift`) — personal tool, machine runs 26, unlocks the glass APIs; research confirms this is the sane floor for a dev-only app.
- **Editor repo home**: in-repo `apps/mac/Sources/EditorCore` vs sibling repo (the web editor lives in `editor/`). In-repo until it hurts; extraction is cheap early.
- **Server OpenAPI wiring**: add the export now or when the Swift client first consumes it (plan 3 decides the mechanism first).
- ~~**Swift language mode**~~ decided: Swift 6.2 approachable concurrency is Apple's default for new app projects — adopted on `MacApp` (`.defaultIsolation(MainActor.self)` + upcoming features). `EditorCore` stays nonisolated: a text buffer must not be MainActor-pinned; practitioners flag background-work code as the place MainActor-default bites.
