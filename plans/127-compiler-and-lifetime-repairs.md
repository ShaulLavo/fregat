## Phase 1 — turn the diagnostics on, then pin them

A whole-function bailout is invisible: the file looks exactly like a file the compiler accepted, and every child re-renders on every render. Nothing in `verify` reads compiler output, and the lint rule that should is structurally unable to. This phase makes the absence visible and then makes it a ratchet, because a warning stream with no baseline is a thing people learn to scroll past.

**What changes.**

1. [`apps/web/vite.config.ts:44`](../apps/web/vite.config.ts) becomes `compiler: { logDiagnostics: true }`. One line. `dist/index.js:238` builds the `diagnostics` array unconditionally, so the flag costs nothing — line 240 only decides whether to print it.
2. `apps/web/vitest.config.ts:9` and `apps/web/vitest.browser.config.ts:35` stay at `compiler: true`, with a one-line comment above the vite change saying why. **What changes.**

`features/search/components/result-file-editor.tsx` — line 117 `const focusTarget = useEditorFocusTarget({` becomes `const { ref: focusTargetRef } = useEditorFocusTarget({`, line 231 `ref={focusTarget.ref}` becomes `ref={focusTargetRef}`. `focusTarget` has exactly two uses and `.focused` is never read.

```tsx
    if (sent) clearDraft()
    setSubmitting(false)

    return sent
  } catch (error) {
    setSubmitting(false)
    throw error
  }
```

**Keep the `catch`.** `composerDisabled` at line 160 is `disabled || submitting` and feeds six consumers; `submitting` is cleared only by that cleanup. Delete the `finally` without a `catch` and any rejection latches `submitting === true` for the life of the mount — editor, attachments, actions and drop target all disabled, and the guard at line 237 rejecting every later send, recoverable only by a remount when `inputKey` changes. `placeChatMessage` resolves before it throws, but both call sites do work outside that promise (`chat-view.tsx:277` builds submissions at 302–305, `chat-draft-view.tsx:89` calls `createDraftSessionSubmission` before awaiting) and a synchronous throw there propagates. The rethrow is of an existing value, so the "never `new Error`" rule is not engaged.

`breadcrumb-symbol-picker.tsx:44-47` and `breadcrumb-folder-picker.tsx:73-76` — replace `const ref = list.containerProps.ref` with `const listFocus = list.focus` and call it in the effect. `use-listbox.ts:170` is `const focus = useCallback(() => ref.current?.focus({ preventScroll: true }), [ref])`, so behaviour is byte-identical and identity is as stable as `ref` was. Leave the `{...list.containerProps}` spread alone; a bare spread does not bail on its own.

Leave the manual memoization where it is. The 24 `memo()` files guard `VirtualList` rows the compiler cannot reach through the virtualizer's render prop, and `virtual-list.tsx:73` is the allow-listed proof of why.

## Phase 3 — stop ordinary navigation killing every terminal

This is the live defect, and it is not one call site. Six direct unmounts detach a connected shell and start the ten-minute countdown, and the technique that makes it stop is already in the file the bug lives in: `terminal-tabs.tsx:51-55` keeps every terminal tab mounted behind `invisible` + `inert`, and switching terminal tabs costs nothing. The layers above it each re-decided the question and got it wrong.

The repair is client-only. The server's kill-on-detach is deliberate and tested with `detachTtlMs: 0`, and raising the TTL would leak PTYs on real disconnects.

Implementation status, 2026-09-20. **Rank 1 is applied** and in the working tree, in two files: `bottom-panel.tsx` keeps the terminal strip mounted behind an `invisible` + `inert` wrapper and renders `DiagnosticsPanel` in the other slot, and `TerminalTabs` took a `visible` prop so a hidden strip passes `active={visible && active}` down. **Ranks 2 through 6 are not applied**, and two of them are harder than this plan first recorded:

- Ranks 2 and 3 wrap a `ResizablePanel` inside a `react-resizable-panels` group, where the technique does not transfer. `visibility: hidden` preserves the layout box, so a hidden bottom panel keeps its share of the group and collapsing it would leave a dead band instead of returning the height to the editor. - Rank 4 was attempted and **reverted**. ## Phase 4 — settle git stage, unstage and discard from the response

The server computes the post-write status and the client throws it away, then refetches the entire `['git']` subtree. Per [AGENTS.md § Async Effects Go Through TanStack](../AGENTS.md#async-effects-go-through-tanstack), a mutation settles the cache before it resolves: `setQueryData` when the response carries the new state, `invalidateQueries` only on the keys it could have changed otherwise.

**What changes.**

New `apps/web/src/features/git/utils/settle-status.ts`, pure and React-free, with `invalidate-workspace.ts` as the precedent. `settleGitStatus(client, rootPath, status)` does `setQueryData<GitStatusResult>(gitKeys.status(rootPath), status)` and invalidates `gitKeys.diffs()`. `settleDiscardedGitStatus` adds `fileSystemKeys.fileSnapshots()` and `fileSystemKeys.trees()`, because discard rewrites files on disk and stage never leaves the index. Write the type parameter explicitly so a future server change fails the typecheck instead of poisoning the cache.

The seven hooks take `rootPath` as a second argument, drop `useWorkspaceInvalidation`, and settle from `onSuccess`'s **fourth** argument:

```ts
onSuccess: (status, _variables, _onMutateResult, { client }) =>
  settleGitStatus(client, rootPath, status),
// One write per repository at a time: a settled cache has no self-healing
// refetch, so two responses must not land out of order.
scope: { id: rootPath },
```

`MutationFunctionContext` is the second argument of `mutationFn` — all seven already destructure `{ client }` there — and the fourth of `onSuccess`. The closed-over client survives only inside `useWorkspaceInvalidation`, and taking it from the context is what keeps a paused mutation settling into its own owning cache. `environment-ownership.test.tsx` pins exactly that: a queued mutation resumes on its owning server after the active server switches. The change strengthens what that test guards.

**`rootPath` must be threaded, not derived.** `useStatus(rootPath)` keys on the caller's path; the response carries `repository.path`, which for a workspace opened at a subdirectory or a worktree is the repo root, a different string. Seeding from the response would write a key nothing observes and the panel would never update — worse than today, because there is no refetch behind it. `filesystemPath()` is a pure brand with no transform, so the caller's string is the key. Reading the active root out of `workspace-state` inside `group-actions.tsx` is rejected for the same reason: a component reading the _active_ root can disagree with the `rootPath` its own `Panel` was rendered with.

Eleven call sites, none of them a callback or a command, so the prop-drilling rule is not engaged and `rootPath` already travels this exact path: `file-actions.tsx` (the component and its three buttons), `change-file-row.tsx:44`, `group-actions.tsx` (the component and its two halves), `change-group.tsx:100` and `:114-119`, `group-menu.tsx:11-22`, `use-group-menu.ts:9`. `use-file-menu.ts` and `features/workspace/hooks/use-row-menu.ts` already hold `rootPath` and only need to pass it — the comment at `use-row-menu.ts:39`, "Same query key the git panel uses", is the confirmation that the seeded key is the one that menu reads.
