## Outcome

Keep static derivations as typed functions next to the data they own, validate shipped inputs during compilation, and emit the finished values. Remove generated TypeScript emitters and runtime preparation where the selected tool proves simpler. Preserve user-data validation, lazy loading, published package contracts, licensing, and the existing appearance.

The four selected opportunities are Approved work after their proof gates. The fifth is an Approved feasibility investigation, with its migration decision recorded here. A missing performance measurement requires a bounded baseline, not abandonment of the work.

## Broader opportunity survey, 2026-10-03

Three read-only research lanes inspected application/shared data, Editor/terminal packages, and server/desktop/build code. Their shortlist was checked against the source and existing ownership plans. Coverage includes web, TUI, contracts, client-core, UI, Markdown, utils, tree, Editor highlighting/keymaps/Unicode/Tree-sitter/TypeScript workers, Ghostty shaders, hotkeys, server catalogs/MCP/provider code, the desktop launcher, Astro site, and generation scripts. This was a broad source survey with traced inputs and consumers, not an exhaustive audit or a runtime benchmark.

The initial four units and icon investigation remain the execution checklist. The following findings extend the evidence and candidate inventory; they are not additional migrations started by this planning pass. A candidate must remove useful preparation or duplicated contracts, preserve its runtime boundaries, and beat the simpler ordinary-data or existing-generator solution. Being technically serializable is insufficient.

### Strong additions to consider after the integration proof

**Language lookup projections.** `editor/packages/highlighting/src/languages.ts:9` expands all installed Shiki language metadata and aliases into a grammar lookup; line 33 builds the document language map. Separately, `apps/web/src/lib/file-language.ts:5–22` merges Tree-sitter aliases, filenames and extension metadata with shared fallbacks, lowercases filenames, and sorts suffixes longest first. Both are fixed data projections suitable for plain emitted records and ordered tuples. Keep their separate policy owners: the highlighting package owns Shiki grammar selection; the web file resolver owns filename/suffix precedence. Preserve lazy grammar loaders, JSX/TSX extension inference, native overrides, equal-length suffix ordering, explicit language hints, Windows paths and runtime shebang parsing. Compare all aliases and resolver cases, use `highlighting/test/service.test.ts` and `apps/web/src/lib/tests/file-language.test.ts`, and inspect chunks to confirm metadata-only inputs can disappear without making grammars eager. Effort S–M, risk low–medium. The web indexes already initialize once; their benefit is simpler shipped data and import preparation, not faster per-file lookup.

**Shared command metadata.** `packages/client-core/src/commands/editor.ts:86–105` projects fixed Editor declarations into titles, descriptions, mutation categories, VS Code aliases, palette policy and TUI keys. `commands/catalog.ts:11–25` joins domain metadata and expands item-position commands into the shared lookup. These outputs are plain data consumed by web command construction and TUI help. Compile the projection and catalog, preserving command order, ids, descriptions and literal declaration types; keep handlers, current bindings, user overrides and availability predicates runtime. This is eligible independently of the executable web command table excluded from scope. Compare every projected field and catalog ordering, typecheck the `CommandId` union, and use web command-table/palette-visibility and TUI keymap tests. Effort M, risk medium, especially type preservation and publication. Removing a metadata-only import edge must be demonstrated in the emitted output.

**Tree-sitter query preprocessing.** `editor/packages/tree-sitter-languages/src/catalog.generated.ts:28` joins query strings and calls `mapQueryCaptures` when a language loads. `src/query-captures.ts:4` scans the full text while preserving strings and comments. The existing `scripts/generate.mjs:40` already computes hashes of the final transformed queries. Compile the joining and capture renaming into per-language lazy query modules. Preserve WASM acquisition, pinned grammar provenance, license notices, dynamic language loading and injection dependencies. Compare transformed bytes to the locked query hashes, check capture behavior, and prove loading one language does not deliver every query. JavaScript, TypeScript and TSX currently share query-source chunks; prepared per-language strings can duplicate those bytes. Compare total query bytes and successive-language loading, not only the first language's laziness. Effort M, risk medium. Compare a macro helper with having the existing generator emit prepared query assets: extending that generator may be simpler. Keeping the asset pipeline does not require retaining this separable runtime text transformation.

**Stock keymap data.** `editor/packages/editor/src/keymap/presets.ts:89` materializes command packs and applies conditions; line 597 derives writable/find/suggestion predicates, and line 624 builds VS Code overrides, filters replaced commands and restores suggest precedence. Precompute stock binding data for each supported platform, then select and compose it at runtime. Preserve custom layers, runtime platform detection, condition evaluation, normalization and trie compilation for arbitrary bindings. Compare every preset/platform/pack, readonly behavior and layer precedence, and measure editor setup rather than key dispatch. Effort M, risk medium. [Plan 206](206-platform-one-keymap.md) replaces the hosted keymap and moves preset ownership: apply this opportunity to its authoritative preset source, not to APIs it plans to delete. Ordinary cached stock data is the baseline; measure the extra shipped bytes of emitting all platform variants.

**Pinned wallpaper catalog.** `apps/server/src/themes/wallpapers/omarchy-catalog.ts:19–24` validates committed JSON and constructs every immutable asset URL at server import. Emit the validated `WallpaperCatalogEntry[]` from the pinned repository/commit/hash/byte metadata. Keep `scripts/themes/generate-omarchy-catalog.ts` as the explicit upstream refresh, and keep installation filtering, downloads and asset-hash verification runtime. Compare entries exactly, make malformed pinned input fail compilation, verify input invalidation and existing wallpaper-library behavior. Effort S, risk low. The payoff is build-time validation and less server preparation; no startup improvement has been measured.

### Examined and kept out of the shortlist

- Tiny static builders: Markdown sanitizer-schema spreading, nine code-fence repair rows, precedence maps, regex fragments and small literal sets are already simple module constants. Compile-time plumbing has no demonstrated standalone benefit. Sanitizer policy also carries a substantial behavior contract for a small construction saving.
- Closure/state construction: Markdown processors, tailwind-merge caches, executable command tables, arbitrary registered hotkeys, editor registries and live terminal/render state have runtime functions or changing inputs. Precompute their eligible descriptors only where a separate useful projection exists.
- Existing multi-output jobs: icon TS/CSS emission, spring-easing CSS, settings schema/reference artifacts and Codex protocol type/schema generation still need explicit output and staleness contracts. A macro does not automatically replace them. Icons retain G5's investigation.
- Asset acquisition and license jobs: Unicode/grammar/dictionary/WASM downloads and dependency notices have provenance or post-bundle responsibilities. Keep those stages. The query preprocessing and bundled-library graph above target only their fixed derived data.
- Live catalogs and releases: installed fonts, network model availability, machine state, user themes, changing prices and release status must remain current. Only committed fallback inputs qualify.
- Astro landing-page frontmatter already runs during its build. No additional runtime derivation was found there that warranted this integration.

The strongest next additions are language projections and shared command metadata, followed by query preprocessing. Stock keymaps need Plan 206 alignment; the wallpaper catalog is a small server pilot. TypeScript library batching and Unicode tables offer potentially larger runtime savings, but their data layout and loading design require a bounded proof before choosing the representation or claiming a gain.

## Scope and constraints

- Keep generators with their domain. A shared adapter belongs in `scripts/compile-time/`; do not introduce a new public package for four consumers.
- Existing integration points: `apps/web/vite.config.ts`, affected Vitest configs, `editor/scripts/build-package.ts`, and Bun's existing source/build entry points. Contracts/client-core export source TS, contracts tests use plain Node Vitest, server development runs Bun source, and Editor ships `dist` JS plus declarations. Client-core currently has no Vitest config; include its own Node transform configuration in the chosen integration.
- The TUI also consumes client-core search through `apps/tui/src/settings/components/browser.tsx`. Its current `apps/tui/package.json` build uses `--packages external`, which leaves shared source dependencies external. G0 must prove its real deployed path and arrange build-time consumption of the affected workspace modules while preserving external third-party/native dependencies. Native Bun source expansion is development evidence; it does not prove that a deployed TUI avoids startup generation.
- Keep contracts/client-core source exports and Editor's published exports. A package-wide conversion to `dist` solely to use macros is outside scope.
- Probe workspace symlinks and optimizer/worker behavior. Bun's macro caller restriction under `node_modules` must be tested against the real symlink layout.
- Match existing typed, readonly contracts. Use `satisfies` or schema-derived types, not casts to pretend an emitted value is validated. Max nesting three. Match structured errors for new failure paths, with observed runtime facts in `internal`.
- No runtime environment values, secrets, home paths, live model catalogs, network downloads or user settings become compile-time inputs. Inputs are checked-in files or pinned installed dependencies.
- Keep runtime schemas/parsers for imported themes, palette editing and stored settings. Do not serialize Valibot schema objects or executable command/React component tables.
- Preserve explicit asset acquisition, compressed dictionaries, lazy TypeScript library imports, tree-sitter assets, palette CSS, settings schema JSON and license notices. They have responsibilities independent of the four derivations.
- Touch package manifests/configs and the lockfile only for the chosen integration. Implementation bumps changed package versions by patch. This documentation pass requires no package bump.
