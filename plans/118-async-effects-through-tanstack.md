# Async effects through TanStack

Status: **IMPLEMENTED 2026-09-14 — all seven units landed in one pass; see [Outcome](#outcome).** Requested 2026-09-14 after the phantom "Unsaved file conflict" on rapid saves. The rule this plan enforces is the "Async Effects Go Through TanStack" section of [`AGENTS.md`](../AGENTS.md); this plan is the migration of the code that predates it.

The survey behind this plan found that git, palettes, session import, provider sign-in and the file picker already run their effects as `useMutation` with a key, an error notifier and cache settlement. Everything else that reaches the server does so as a bare `await` behind a local boolean, a hand-rolled retry loop, or nothing at all. Thirty sites, listed per unit below. The save path is one of them, and the reason the conflict bug was a "busy" error instead of a queued second save.

## Decisions

| Decision                                          | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 — one runner outside React                     | `apps/web/src/lib/mutations/run.ts` exports `runMutation(queryClient, options, variables)` which runs the options through a `MutationObserver` on that client, the same primitive `useMutation` wraps, so client mutation defaults, retry and scope all apply. Services, command handlers and toast callbacks use it. Hooks use `useMutation` with the same `mutationOptions` object, so a feature defines each effect once in `utils/mutations.ts` and executes it from either side. |
| D2 — one notifier                                 | `apps/web/src/lib/mutations/notify-error.ts` exports `createMutationErrorNotifier({ area, title })`. Git's file becomes one call to it. Every mutation in this plan passes the feature's notifier as `onError`.                                                                                                                                                                                                                                                                       |
| D3 — intents stay, but they run inside a mutation | Where a Plan 113 intent queue owns projection, the `mutationFn` is the `runIntent` call and the mutation contributes only the key, the scope and the notifier. The queue still owns optimism and acknowledgement. This reverses 113's "no React wrapper" for the sole purpose of making the effect visible to `useIsMutating` and devtools. **Needs confirmation.** The alternative is to leave the four intent sites as documented exceptions.                                       |
| D4 — serial by scope, never "busy"                | Every mutation that can be issued twice while in flight carries `scope: { id }`. Same-scope calls queue. The second call re-reads its input when it runs and returns early if there is nothing left to do. `runWorkspaceMutation` keeps its reservation for computed workspace edits, but no user-facing save path throws `workspace-edit-busy` any more.                                                                                                                             |
| D5 — settlement is part of the mutation           | `onSettled` writes the cache with `setQueryData` when the response carries state, or `invalidateQueries` on the keys the effect could have changed. Where the truth lives in a Zustand projection (chat shell snapshot, environments), `onSettled` refetches that projection through the existing sync helper. A mutation resolves after settlement, not before.                                                                                                                      |
| D6 — POST-shaped reads become queries             | Session search and workspace root validation are reads with a POST transport. They get `queryOptions` with a key, a `staleTime`, and the query's own abort signal. **Root validation needs confirmation**: `openWorkspaceRootPath` also claims a server-side open generation, so if that claim is load-bearing it is a scoped mutation instead of a query.                                                                                                                            |
| D7 — project registration is a query              | `registerCheckout` returns a stable `worktreeId` for a root and is called from two places with no dedupe. It becomes a query keyed by root path with `staleTime: Infinity`, so both callers share one POST. **Needs confirmation** that registration has no side effect a second call would need to repeat.                                                                                                                                                                           |
| D8 — local pending flags are deleted              | Every `useState` named `pending`, `saving`, `working` or `busy` that mirrors an effect is removed. The component reads `isPending` from the hook or `useIsMutating(key)`. A `Button` renders `Spinner` from that.                                                                                                                                                                                                                                                                     |
| D9 — retries belong to the mutation               | `retry` and `retryDelay` on the options, fed by the domain's existing policy functions. No loop inside `onSuccess`, no `setTimeout` backoff in user code.                                                                                                                                                                                                                                                                                                                             |
| D10 — documented exceptions                       | Terminal input over the socket, orchestration WebSocket frames, and the HTTP fallback inside the chat transport are transports, not effects, and stay as they are with a comment naming this plan. The workspace-edit lifecycle keeps its reservation because it is a multi-step transaction, not a request.                                                                                                                                                                          |

## Outcome

Landed 2026-09-14, uncommitted in the working tree, deployed to the mesh as release `plan-118`.

- D3 confirmed: the four intent sites (`runTreeIntent`, rail order, chat messages, and the tree drop-move through `runTreeIntent`) run inside a keyed mutation whose `mutationFn` is the `runIntent` call.
- D6 resolved: root validation runs once per workspace mount, not per navigation event, so it shares the open-root mutation options with the root switch instead of becoming a query. No scope: a validation must not queue behind a root open the server is still holding.
- D7 confirmed: project registration is a query with `staleTime: Infinity`; the panel and the kill path share it.
- The save path keeps `runWorkspaceMutation` inside its `mutationFn`. The reservation is not the lock there any more; it is how the workspace-edit history learns a path moved forward. The `saving` member of the sync state stays unused; the watcher refresh instead waits on the mutation cache for a pending save of the same document, which is the same guard without a second source of truth.
- Environments: connect, disconnect and the auth answer are keyed mutations without a scope. The connection service already had the right protocol (a join map so two callers share one attempt, and an abort that reaches the running attempt before a replacement starts), and a scope queued a replacement behind the attempt it had just aborted. The mutation wraps only the transport: the prelude that records intent, restores cached bindings and sets the launching phase runs synchronously before it, because a reconcile that follows in the same tick depends on that state. The SSH recovery test caught both.
- Remaining `useState` flags are composites, not mirrors of one effect: the machine form's `saving` spans a settings intent and a connect; the dirty-close dialog's `saving` spans the saves and the tab close. They stay.
- Session search was already a query and the settings transport already a scoped mutation; the survey overstated both. The settings change is only the epoch loop moving into `mutationFn`.
- Verification: `bun run typecheck`, `oxlint` on every changed file, the per-unit tests named above plus new `save-service.test.ts` (overlapping saves write once; an edit between queued saves writes twice), `event-conflict-adapter.test.ts` (a double click issues one write), and `lib/mutations/tests/run.test.ts` (same-scope mutations run serially). The rapid-save browser test was not written; the node test covers the ordering it would have.
